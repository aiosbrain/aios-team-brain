## Findings

**Blocker 1 (High): a scope change waives every provider minimum.** Document restrictions and account holds are keyed by generation. A scope change allocates a new generation, so the adopter ignores the old section, the standing-set helpers filter by the new generation, and the first checkpoint of the new generation drops the old section from the brain's document.
- Trigger: a document holds an unrepresentable (never-lapsing) or multi-year restriction. The Admin adds or removes any root. The next run reads that document immediately.
- Expected: the adjudication says "Do not use scope changes, queue replacement or rescan as an implicit override" and F4 says "Scope change is not an approved recovery workaround". A provider's Retry-After binds the account and document at Google, not a selection generation.
- Actual: `ingestion/aios_ingest/gdrive_sync.py:265-301` returns early on a generation mismatch, `gdrive_sync.py:236-245` and `:200-208` read only the current generation, and `gdrive_sync.py:3130-3141` rebuilds both sections for the current generation only, which `coordinator_document` then publishes wholesale (`ingestion/aios_ingest/connector_state.py:60-87`). The SQLite rows survive but are never consulted again.
- Impact: the F4 "no override" decision is void. Any scope edit is a one-click early retry, including for the fail-closed sentinel. The same applies to the R47 account hold.
- Note: the adjudication's own table says "with generation/context validation", so the writer followed one line while breaking another. Astra must resolve that tension. My recommendation is to key restrictions and holds by connection, account and provider id, record generation as context, and carry forward any still-standing entry into the new generation's published section.
- Regression: restrict a document with the sentinel, publish, bump the execution's generation in the double, run with rearm, assert no read of that document and that the published section still names it.

**Risk 2 (Medium): rearm now keeps the local backoff, not only the provider minimum.** The eighth failure stores `not_before` as the later of backoff and provider deadline (`gdrive_sync.py:126-137`); backoff at seven failures is roughly one to two hours. Rearm no longer clears it (`ingestion/aios_ingest/state.py:1622-1634`), so Run now or Retry within that window neither retries the document nor reports why: `retry_exhausted` is cleared and the row is simply ineligible.
- Expected: the adjudication's narrow correction was to preserve the provider deadline. With `document_restrictions` now the owner, the backoff component only delays an explicit Admin action.
- Evidence of masking: every coordinator-level test zeroes `_backoff_seconds` (`ingestion/tests/test_document_restrictions.py` clock fixture, `test_exhaustion_is_not_completion.py:3727`), and `test_rearm_resets_the_attempt_budget…` pins the new behavior with a year-2099 value.
- Regression: real backoff, exhaust a non-restricted document, run with rearm at once, assert it is read (or assert a named diagnostic if the wait is the intended product behavior).

**Risk 3 (Medium): a non-quota deferral before any stream exists opens an account hold.** `_open_account_hold` holds the account for every deferral except the two local-deadline categories (`gdrive_sync.py:301-341`), and it is called for root binding, relocation re-reads, the service-account identity read and start-token capture (`:1126-1129`, `:1164-1166`, `:1228-1230`).
- Expected: the writer prompt says "Do not route nonquota deferrals as account holds" and ARCHITECTURE now says "A per-document 503 is never an account hold". In the drain and change-page paths that rule holds.
- Actual: one root's 503 carrying a valid Retry-After holds every stream and every later run for the full provider deadline, and publishes it. A transient timeout on start-token capture becomes a published hold too, though only for the fallback's few seconds.
- Coverage: `test_account_hold_before_streams.py` parametrizes only `rate_limited` and `dispatch_deadline`; the root-phase cases in `test_retry_after_holds.py` all use status 429. No test sends a 503 to a root read.
- Regression: root metadata answers 503 with Retry-After 99999999 while another root and drive are readable. Assert no account hold, the other stream runs, and the root is unresolved or uncertain with that deadline.

**Risk 4 (Medium, design): a restricted selected file root freezes its stream in baseline.** In a rescan or fresh-state rebuild the root's page is never materialized and the baseline returns incomplete (`gdrive_sync.py:2286-2307`, `:2466-2472`), so the stream never reaches catching up and no edit to any other document in that drive is observed until the restriction lapses. For the sentinel that is forever.
- The initial-baseline case is fine because baseline pages commit without acknowledgments (`:2542`). The gate bites only after a 410 rescan, rebind or fresh state, which is exactly when `test_a_restricted_selected_file_root_is_not_read_by_a_controlled_rescan` runs, and that test does not assert that later edits to the other file still flow.
- The adjudication asked to "Preserve independent-document progress". Materializing the page without a read would wrongly infer absence, so the clean fix needs a decision: carry the prior snapshot's membership for that root into the new snapshot without a provider read, or accept and document the freeze.

**Risk 5 (Low): automatic publication checks the tombstone before the existing-owner conflict.** `lib/identity/member-identities.ts:148-152` returns `tombstoned` whenever mapping state is `unlinked`, before `:195-199` would detect a row held by another member. Normal writers cannot produce that shape, but a raw legacy row plus an unlinked state would publish the credential without the 409 review page. Move the conflict test ahead of the tombstone return and add one data-mechanics case.

**Risk 6 (Low): a permanently refused post-push checkpoint re-pushes forever with no backoff.** `_push_doc` now treats every non-terminal checkpoint error as control-plane and calls `fail_work` only for a deferral with a date (`gdrive_sync.py:2667-2681`). A 4xx the brain returns on every attempt, such as an oversized progress document, re-pushes the same content each poll with only the error code as diagnostic. Adjudicated as stage-based, so this is a follow-up: cap or report repeated control-plane refusals of one obligation.

**Risk 7 (Low): diagnostics gaps.** The change-page path records unavailable detail but never counts `selection_root_unavailable` (`gdrive_sync.py:1971-1978` versus `:2248-2257`). A restriction whose checkpoint fails has no `…_unpublished` counterpart to the account hold's; only the checkpoint's error code is reported, though the adjudication asked to "report that remote durability is unconfirmed".
