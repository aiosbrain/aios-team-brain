## Outcome and actual problem

On a markerless fleet, boot, scheduler and confirmed operator command must use the same frozen SQL reconciliation and its post-lock substrate check as PRET-6 preDeploy. A fleet **observed at that check** with content and zero context memberships must fail without stamping a marker or modifying builtin membership. Confirmed CLI must remain safe when a team deletion removes the only partitioned corpus after its advisory state read. A marked fleet remains an immediate no-op preserving deliberate membership changes. This is initial/post-lock state refusal and the proven team-cascade race closure, **not** an unconditional at-commit substrate guarantee: independent item/project/context deletion after the check remains unfenced.

Current `lib/access/groups.ts:204–292` repeats the reconcile in short autocommit statements, reading the marker but no substrate. `instrumentation.ts:52–53` and `lib/ingest/scheduler.ts:71–72` call it directly. `lib/access/materialize-command.ts:107–127` separately checks state then calls it at 130; a committed cascade can make that check stale. SQL `postgres/schema.sql:2987–3089` already has the settled fail-fast and post-lock substrate checks, marker-last ordering and frozen algorithm. Markerless runtime reachability requires a restore beneath a running app or marker deletion; do not describe ordinary deployments as always vulnerable.

The missing-substrate hazard is denial/blackout at cutover, not a disclosure claim: missing item context fails reads closed. The existing predicate is deliberately fleet-global existence of **any** partition row; it is weaker than complete or per-team partitioning and must not be strengthened here.

Bare RPC is unsafe: `lib/db/pg/pool.ts:69` caps a whole statement at 30 seconds, whereas the old TS implementation makes many short statements. A slow single-statement fleet reconcile could repeatedly roll back. The local finite execution policy and capacity/readiness proof below are part of this fix, not an optional cleanup.

## Service-owned transaction design

1. Keep exported service name and existing success shape `{ok:true, ran:boolean}`. A boolean SQL true means this invocation reconciled/stamped; false means already complete. Validate returned data is exactly a boolean. Null, missing, object or string responses are named failures, never success.
2. Require `TransactionCapableDbClient` using current `isTransactionCapableDbClient`; missing capability fails closed. A nested/bound PgClient rejects through its existing transaction guard; do not escape to the global pool or run an unbounded bare RPC fallback. Runtime DB is PostgreSQL (`lib/db/types.ts`); fake client behavior is not a supported runtime escape.
3. Start exactly one new owned `db.transaction(session => ...)`. Establish READ COMMITTED **before any snapshot-creating statement**, so the SQL post-lock check sees a deletion that committed while it waited. Do not accept caller repeatable-read/serializable snapshots or silently reuse an ambient session.
4. Set finite transaction-local **`statement_timeout = 120000ms`** and `lock_timeout = 2000ms` on the same session connection before the function SELECT. Required order: engine BEGIN → SET TRANSACTION ISOLATION LEVEL READ COMMITTED → transaction-local timeout setup → function SELECT → callback validation → engine COMMIT. `SELECT set_config` is snapshot-creating and must not precede isolation setup. Use `session.executeSql` and parameterized SET mechanisms. This v2 requirement **supersedes v1's 300,000ms cap**: 120s is twice the required <=60s measured envelope and reduces orphan/writer exposure. No environment-wide/zero/unlimited/inside-function/connection-global setting; no production test hook or generic timeout framework.
5. Use only `session.executeSql("SELECT materialize_builtin_membership_once() AS result")` inside this service. The existing bound executor records thrown failures (`tx.ts:228–235`), so no adapter RPC addition or error-envelope path is needed. Require exactly one result row with a boolean result; do not default missing rows to false. Add a reactive caller guard scanning production `lib`, `app`, `scripts` TS/TSX with comments stripped: this exact SQL function invocation/name may occur only in the owning service, no public `.rpc` entry. Tests, docs and frozen SQL/migration owners are separate sanctioned surfaces. Do not query an aborted transaction to restore settings; ending the owned transaction supplies restoration.
6. Convert proven ordinary failures to `{ok:false,error}`. Catch existing `TransactionExecutionError.unknownCommit` separately, preserving it as optional `outcomeUnknown:true`. Never report `ran:true` before transaction commit has been acknowledged. Existing engine owns BEGIN/COMMIT/ROLLBACK and connection release/discard; reuse it rather than reimplementing cleanup. Every path ends this owned transaction, so local settings disappear on normal release; uncertain connections are discarded instead of recycled.
7. Add optional `outcomeUnknown?: true` to the CLI's compatible `MaterializeResult` type. Such failure exits nonzero and says marker/state may already have committed and must be checked. Ordinary service failures with known rollback retain their existing failure behavior. The CLI's separate unexpected-throw catch also stops asserting no stamp: an unclassified throw has no confirmed outcome, so report that uncertainty and recheck guidance. Both existing false-certainty suffixes are covered. Confirmation, staging discrimination, dry run, zero-team and concurrent ran:false success output remain unchanged. Boot/tick keep log/retry/ledger behavior with uncertainty in error text.

Next 16.3 `register` is awaited before readiness. Normal deploy preDeploy already executes the owner and stamps before runtime; deploy refusal prevents boot. Markerless boot is recovery/restore/marker-loss reachability; copied staging skips boot/tick entirely and can supply only CLI evidence. Railway healthchecks gate new-deployment activation, not continuous health; no restart healthcheck guarantee is established. [Railway healthchecks](https://docs.railway.com/deployments/healthchecks). AC-12 retains actual absent-marker/non-copied/ran:true production-Next local startup<120s as **tested-profile recovery liveness evidence**, not a claim about Railway restart admission or all configurations. Ordinary marked startup is measured separately. No hosting changes.

120s is a **per-statement server cap**, not a total transport/transaction wall-clock deadline. After client process death, an orphan query can continue holding locks until statement cancellation/completion; do not promise prompt disconnect or immediate lock release. The existing idle-in-transaction60s cap applies once a backend idles, not to an executing statement. No automatic replay after uncertainty. We deliberately do not add required `client_connection_check_interval`: PG 16 supports multiple OS families, contrary to the review's Linux-only premise, but kernel-reported closure and TCP detection remain conditional, and older/unsupported platforms may reject configuration. A mandatory new compatibility dependency is unnecessary for the scoped fix's finite server cap; optional operational tuning is deferred. [PostgreSQL16 connection settings](https://www.postgresql.org/docs/16/runtime-config-connection.html).

Locks are held through acknowledged transaction completion. During markerless reconcile, ordinary authority/admin/connector writes can queue/fail, governed operations can reach1.5s lock limits, and concurrent preDeploy DDL can hit loader15s lock timeout and abort. Capacity evidence must report actual/upper-bound lock-hold duration, writer wait/refusal and release, not only SELECT throughput. Operators must avoid concurrent deploys/destructive writers during attended markerless recovery; do not represent<=60s as zero interference.
