# AUDITFIX-19 — require an explicit scope decision when minting an agent token

Version 2.2, final LOW clarifications following CLEAN Opus v2 and supplemental review: preserve raw schema identity, guard whole requests before capture, consume captured audit legs, use test-owned pause seams and genuine grant fixtures. Spec author: GPT-6.1 Sol, high reasoning. Ticket [AIO-1050](https://linear.app/je4light/issue/AIO-1050/an-agent-token-can-be-minted-with-no-project-scope-and-that-is-the), brain row `AUDITFIX-19`, verified In Progress. Base: staging `6789122a868d885045bc92aa915db7dd4c4dc782`, following PR736. New file to create after acceptance: `docs/design/auditfix19-explicit-agent-scope.md`. No implementation is authorized to start until required spec/security review and exact Linear spec attachment are complete.

## Problem and outcome

Today an admin can call `mintAgentTokenAction` with a launcher and valid expiry but no scope and receive a token inheriting the launcher's entire live project visibility. The low-level guarded mint writer also treats omitted scope as NULL. The UI already blocks submission until the admin chooses a scope, so rebuilding the form does not fix the server boundary.

Every new mint must carry a deliberate, machine-readable choice: a nonempty list of projects, or all projects reachable by the launching identity as its access changes. Saying nothing refuses the mint and creates no credential. Existing stored credentials retain their exact live scope semantics. This changes the issuance contract; it does not change which content a verified token may read.

## Scope and decisions

In scope: shared scope type/runtime validation, guarded mint writer, admin request policy/action, existing form payload mapping, caller/fixture adaptations, regression tests, focused documentation. The one credential writer remains `lib/access/agent-tokens.ts`.

This is one PR for the existing admin credential-mint surface and its single writer. Excluded credential-consent policy would need a separate spec; AIO-1046 curation is deferred to its existing follow-up issue and remains excluded until a curation surface exists.

Excluded: new routes, schema or membership migrations, historical credential revocation/backfill, token wire format, token verification/expiry/revocation policy changes, read enforcement changes, new admin-role checks inside the service, acting-as consent work, delegated writes, new curation surfaces/AIO-1046, launcher UI rebuilds, CLI features, generic access audit, unrelated historical doc repairs, production census/deploy/merge.

Routine product choices are decided as follows:

1. Missing or malformed scope is an error, rather than a default list or an automatically empty token. The admin must fix the request; no successful-looking dead credential is issued.
2. Use one discriminated scope choice, not a truthy flag plus an optional list. It makes all-reachable and selected-project modes mutually exclusive, works in serialized action payloads, and can be runtime-validated at both boundaries.
3. New minting of empty scope is refused at both service and action. **Persisted empty tokens remain valid credentials that read nothing**; no normalization to NULL or invalid-auth state is permitted. Test-only legacy fixtures continue proving that contract.
4. All-reachable is a dynamic choice for any eligible same-team launcher, including a launcher distinct from the minting admin and future grants to that launcher (and represented leg intersection if the internal service uses acting-as). It does not enumerate a mint-time snapshot and is not intersected with the issuer's project visibility. Selected-project mode keeps its existing requirement that both admin and launcher can see each requested ID. This asymmetry is deliberate and is a mode-specific issuance policy, not a blanket guarantee that an admin cannot provision credentials reaching another member's projects.
5. The low-level service stays a server-only primitive that validates eligible legs, not a new public admin endpoint. `actorMemberId` remains audit provenance. The existing action is the authenticated admin boundary. Explicit choice is not a new authority grant and must not be represented as evidence of UI interaction.

No unresolved product choice remains after completed independent reviews and Astra adjudication. A newly evidenced substantive authorization issue must be adjudicated explicitly rather than silently widening this slice.

## Required request contract

Use a shared framework-free type, with equivalent naming permitted only if semantics stay exact:

```ts
type TokenMintScope =
  | { kind: "all-reachable" }
  | { kind: "projects"; projectIds: string[] };

// Existing other fields keep their service/action-specific rules.
interface MintArgs {
  memberId: string;
  scope: TokenMintScope; // required; no projectScope compatibility default
  onBehalfOf?: string | null;
  name?: string;
  expiresAt?: string | null;
}
```

`MintRequest` also requires this `scope`. UI untouched state may remain null, distinct from either valid serialized choice. `AgentTokenPrincipal.projectScope`, `Principal.projectScope` and the DB column remain `string[] | null`; the mint request and verified read principal deliberately have different types/representations.

Implement shared pure scope parsing/validation usable by the action policy and core writer. It must accept untrusted runtime input and return a refusal, rather than throw or rely on TypeScript. At core entry, and at public action entry after the existing admin authorization gate, guard that the whole request is a non-null, non-array object before reading or capturing any request field. Null, primitives and arrays return the existing invalid-request refusal with no credential row or successful mint audit; they must not throw during field capture. The caller must provide an own `scope` property with a non-null, non-array object and an own exact discriminant. All-reachable carries only `kind`; a project choice carries only `kind` and an own `projectIds`. Reject missing/undefined/null/inherited scope, primitive/array scope, unknown kind, stray/conflicting scope fields (including projectIds on all-reachable), missing or non-array projectIds, empty list, non-string/invalid UUID IDs, duplicate IDs and lists beyond the existing 200-project cap. `Object.hasOwn(request, "projectScope")` means refusal at either issuance boundary **even if its value is undefined or null**, including alongside a valid new choice. The form must not emit the legacy key at all.

Snapshot before validating: read the owned discriminant and projectIds value once, capture the array length and enforce the existing length bound, then copy every index into a new dense array using an indexed loop. Missing holes become undefined and are rejected rather than skipped by `.some`/`.every`. Validate every snapshotted entry is a UUID string; accept case-insensitive UUID spelling, lowercase it, then check duplicates on the canonical strings (mixed-case duplicates are refused, never silently deduplicated). The canonical copied list is the only value consumed after validation; no second read of the raw list/discriminant may change it. Return normalized data, not only a boolean while callers later forward raw input.

Core performs this before its first service database read or secret generation. Public action keeps authorization first; after its admin gate it parses/copies before its first scope-related await. Its BOTH subset checks and the scope forwarded to the writer consume that same normalized copy. Core independently copies again and uses its own normalized result for insertion and scope audit metadata. A later writer copy does not repair an action that checked raw mutable values. No `?? null` applied to an absent request scope may remain as an issuance fallback.

Capture the other request fields used for validation, authorization or persistence alongside the scope: launcher memberId, onBehalfOf, name and expiresAt. In the action, capture after the admin gate and whole-request object guard, before field validation, then use those captured/validated values for visibility queries and the writer call; do not re-read raw input after an await. Keep own-key legacy rejection/inherited-scope checks against the actual input so selective field capture cannot hide them. In the core, capture the fields after its entry object guard, validate scope independently, and use the captured launcher/represented identities for member reads, insertion and the subsequent mint audit meta.member_id/on_behalf_of. Use captured name/expiry for persistence. Audit legs must agree with the inserted row even when the original caller object changes while an await is pending. This is a bounded in-process snapshot guarantee, not a new expiry/acting-as/identity policy in the core. Tests mutate original launcher/name/expiry as well as scope while an action visibility read or core member read is paused and prove the originally validated/captured values are the ones consumed. Normal serialized action requests keep identical intended behavior.

Normalize **valid choices only**:

| Valid new request | Persisted `project_scope` | Runtime meaning |
| --- | --- | --- |
| `{ kind: "all-reachable" }` | NULL | No token attenuation beyond live member-leg visibility |
| `{ kind: "projects", projectIds: [P, ...] }` | Canonical lowercase copy of that nonempty ordered ID list | Live visibility intersected with this fixed ID list |

Public action keeps its own `requireTeamAdmin` gate first and derives team/admin identity from the gate. Keep existing self-only, identity shape, name, required bounded expiry validation. Scoped requests retain BOTH admin-visible and launcher-visible subset checks against the normalized IDs; neither role check nor list check moves exclusively into the form. On read failure or invisible/foreign project, scoped action returns refusal and writes nothing. All-reachable performs no project enumeration, retains existing eligible-leg checks, and may mint when the picker is empty if the admin explicitly selects it. This is not proof the launcher has nonempty visibility: a valid all-reachable token can currently see zero and gain grants later.

Here issuance visibility means the **existing writer/destination predicate** `visibleProjectRows` in `lib/access/enforce.ts:328`, including its legacy posture/provenance behavior; it is not synonymous with membership read visibility. Use that exact helper to establish BOTH issuance test preconditions. The read authority/outcome remains `effectiveVisibleProjects` and the token content route. In the asymmetric A/L/Q fixture, A must be a real team-posture admin (e.g. promote `seed.memberId` to role admin, preserving its explicit Everyone placement from `seedTeam`/`placeMemberByTier`), not a bare member with a mocked admin role and no posture membership. Give Q no hand-entered tasks/decisions and no item/container whose unrelated current curation grants issuance reach to A; place any Q outcome item only into Q. Establish Q absent from A's `visibleProjectRows` set and present in L's set before asserting selected-mode admin refusal, then prove explicit all-reachable reads Q using the read oracle/route. Preserve the converse and both-visible controls using these same predicates. All asymmetric and positive controls establish issuance visibility through actual grants/current curation, with no hand-entered task/decision shortcuts or unrelated curation reach; this fixture restriction applies to every project in those cases, not only Q.

Action visibility-error and paused-mutation seams live in tests only: mock the module export with a default pass-through to its original implementation and a resettable hoisted test switch/deferred promise. Never add injectable action arguments/options, runtime environment hooks or production test parameters anywhere for test convenience, including a `use server` export, mintAgentToken or MintArgs. For the core member-read pause, use a test-owned decorator of the already existing db argument, or synchronously mutate the original args immediately after starting mintAgentToken and before its pending await resumes. No internal getMember export or production hook is needed. Pair each injected error refusal with a same-input uninjected successful control and assert no token/id/row/mint audit. Reset the seam between cases so unrelated assertions remain genuine.

Core writer runtime-validates scope independently, even if the action already did. It keeps existing launcher/represented eligibility, same-team and Phase A external-tier checks. Core explicit project lists need not be currently visible: their authority remains intersection-only, as before; the public admin action retains its stricter selected-project issuance subset checks. Do not apply action-only acting-as or expiry restrictions to this internal primitive as a side effect of sharing scope validation.

## Invariants, effects and errors

The source of read authority stays current group memberships/project grants through `effectiveVisibleProjects`. Formula remains `V(launcher) ∩ V(represented ?? launcher) ∩ (storedScope ?? U)`. NULL is universe only for attenuation, never an instruction to read the whole team. `[]` is empty. Token authentication keeps original same-team leg FKs, strictest tier/external refusal, hashed secret, expiry/revocation and live eligible-leg checks.

Invalid scope returns `{ ok: false, error }` with a useful scope-specific message, no token/tokenRowId, no `agent_tokens` row and no successful `access.token_minted` event. Public unauthenticated/non-admin requests still get the existing refusal without exposing privileged details. No credential secret is added to validation errors, logs, URLs or audits.

After insertion, return/show the bearer token once and retain existing best-effort revalidation; do not turn a post-mint cache fault into an apparent refusal. Successful audit metadata retains `scoped` and `scope_size` derived from the validated persisted choice; adding a nonsecret explicit mode label is optional, not a new schema or completion requirement. No successful audit is emitted for scope refusal. Existing audit delivery failure behavior is not changed by this slice.

This is not a grant transaction: grants may change between action checks and mint. Subsequent reads rederive authority, so selected projects can disappear immediately and all-reachable can track future grants. Copying the request prevents input mutation; it does not freeze live authorization. Revocation/deactivation affects later requests; no new promise to kill an already running stream is made.

Mint is not idempotent today. A transport failure after success can leave a credential whose secret is lost; do not add blind retries or an idempotency scheme here. Keep existing list/revoke recovery and never manufacture a second success from a refused request. Stale pre-update UI requests may fail due to missing scope/action IDs: give the normal error/refresh path, not a backwards-compatible permissive fallback.
