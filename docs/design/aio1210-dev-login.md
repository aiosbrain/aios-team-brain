## Problem and intended outcome

`app/auth/dev-login/route.ts:14–35` can sign a session for any query email after only a production-mode check. It creates/upserts the identity and links matching non-disabled memberships through `lib/auth/pg-login.ts:18–55`. It does not create membership/role grants, but impersonating an existing member email supplies that user's identity. `lib/auth/pg-session.ts:27–33,48–60` signs a 30-day host-only httpOnly cookie. Proxy protects `/t/*`, not this route (`proxy.ts:9–20`).

This is conditional hardening of a reachable development/custom server. Ordinary `next start` assigns production when NODE_ENV is absent; normal production compilation also substitutes production, and Dockerfile line 38 sets it explicitly. An unset shell variable on that ordinary path is not a demonstrated production bypass. Installed Next 16.3 env and CLI guides establish these mode defaults and that dev listens on 0.0.0.0 by default.

Developers deliberately enable the bypass for a loopback-bound local server. Requests outside the precise admission predicates below receive 404 before identity writes or signing; a spoofed local authority on a mistakenly exposed enabled listener can satisfy those predicates. A Host header proves request authority, not remote peer identity: a remote client can spoof it if an enabled listener is exposed. The accepted boundary therefore requires explicit opt-in, unconditional production denial, strict local request authority, and documented loopback binding. It does not promise network-peer exclusion for an operator who publicly exposes an enabled dev listener.

## Admission contract

Production always denies, including `AIOS_DEV_LOGIN=1` and obsolete `ALLOW_DEV_LOGIN=1`. Every nonproduction mode (including direct-handler unset/test cases) additionally requires **exact** `process.env.AIOS_DEV_LOGIN === "1"`; whitespace, true, 0, empty and missing are not opt-in.

Admission order: production guard → opt-in guard → local Host/URL/forwarded authority validation → safe redirect preparation → ensureAuthUser → linkMemberByEmail → signSession → response/cookie. All refusals use 404 with the constant existing body `dev-login is disabled`, `Cache-Control: no-store`, no Location and no Set-Cookie. ### Exact request authority rules

Host means `request.headers.get("host")` as exposed by the framework, never x-forwarded-host or request.url as its substitute. Missing Host denies. Parse that value with an explicit lexical allowlist **before URL canonicalization**:

- Accepted host tokens: ASCII case-insensitive `localhost`, exact `127.0.0.1`, or exact bracketed `[::1]`.
- Each may omit a port or carry `:` followed by canonical decimal 1–65535 (1–5 digits, no leading zero). Absence uses the request URL scheme's default port, 80/443.
- Reject trailing-dot/subdomain/suffix forms, other loopback numeric representations or addresses, unbracketed/expanded IPv6, zone IDs, userinfo, whitespace/control characters visible to the handler, comma lists, path/query/fragment delimiters, empty/signed/zero/out-of-range ports and extra colons. Browser/Node may reject some raw malformed bytes before the handler; do not claim those reach it.

Parse request.url safely. Its scheme must be http: or https:, credentials empty, and parsed hostname one of localhost/127.0.0.1/[::1]. Its effective port must equal the Host's effective port. Loopback hostname aliases may differ: Next dev can normalize a browser 127.0.0.1 URL to localhost, so equality of literal host strings is not required. A public URL authority does not become admitted merely because Host/forwarded Host is local.

If x-forwarded-host is absent, it adds no authority. If present, it must be a single value accepted by the same strict Host grammar and normalize to the **same hostname and effective port as raw Host**; other aliases, public values, lists or malformed values deny. This permits Next's own local header population while forbidding a forwarded override. If x-forwarded-proto is present it must be exactly http or https and equal request.url's scheme without colon; lists, other values or mismatch deny. RFC Forwarded, x-forwarded-for and other headers are not authorities and never enter redirect construction. No DNS or peer-address inference is performed.

Build the redirect base only from validated raw Host and the validated request URL scheme, never a forwarded value. Case/default-port normalization may occur; hostname and effective port remain the admitted Host's. Both http and local experimental https remain supported at the handler level. This does not introduce a production bypass or promise universal proxy compatibility. Host port remapping (for example an SSH/devcontainer published port differing from the render server port) deliberately refuses under the equal-effective-port rule; use direct same-port loopback access for this bypass. request.url hostname is configured/fallback server metadata, not bind/peer attestation. An explicit server URL hostname 0.0.0.0 is outside the local URL allowlist and refuses; an omitted-bind launch can expose a localhost fallback and admit spoofed local authority. Restricting URL hosts to IP literals is not adopted: it would remove documented localhost compatibility without proving peer identity. The required loopback launch and exposed-listener residual remain explicit.

Installed Next16.3 next-server.js derives its init URL scheme from x-forwarded-proto, and base-server.js preserves/populates forwarding. A plain-HTTP wire request with an exact https header may therefore expose request.url as https too and pass the stated equality rule, yielding an https **local** redirect. That is allowed request-authority behavior, not proof of TLS and not a promise that such a redirect is usable. Invalid/list protocols and contradictory forwarded Host are wire refusal controls; independently mismatched exposed URL/header schemes and public request URLs are direct-handler controls where the standard server may not expose that mismatch.

### Identity, redirect and failure compatibility

Preserve `email = searchParams.get("email") || "alex@demo.aios.local"`: absent/empty uses the existing demo default; explicit emails are passed unchanged to the existing writers. No new member/role/tier creation, activation policy or password flow is introduced. Keep absent next default `/t/demo`; feed that selected value through existing `safeNextPath` before resolving against the local base. Empty/absolute/protocol-relative/unsafe next falls back to `/`; safe path/query/hash stays usable, including the helper's existing normalization.

The old `startsWith("/") && !startsWith("//")` check permits a backslash target to resolve off-origin. `lib/auth/next-path.ts` already documents and closes that exact escape. Reusing it is necessary to make this route's new local-authority guarantee coherent, not a general redirect-policy expansion. The final redirect origin must equal the validated base's origin; no query or header can switch it. Prepare/validate the destination before any identity write.

An admitted success retains NextResponse.redirect's 307 and existing SESSION_COOKIE/options, and **adds** explicit Cache-Control: no-store (the baseline success did not set it). No cookie domain is introduced, signer/expiry policy unchanged. Existing DB/signing failures propagate through normal framework failure handling; do not convert them to successful/denied login or replay them. No successful cookie response is returned on failure. An admitted request may have completed an identity write before a later failure, as today: no transactional rollback or new retry promise. Turning opt-in off prevents future minting but does not revoke previously signed sessions. A credential-free GET can be induced by a browser/top-level navigation while the local tool is enabled; loopback binding is not per-request human approval or CSRF defense. No new Origin/fetch-metadata/nonce policy is promised. An attacker-domain raw Host denies, without a blanket DNS-rebinding/browser-security claim. Never enable this tool against a staging/production/shared database or AUTH_SECRET: the current signer has no environment audience, so a token is portable to any instance accepting the same signing key and identity. No signer/revocation policy change is in scope.
