# Staging workflow hardening

Version 3.2 · 2026-09-09 · AIO-997 · base `0006d51f798deebdd008855767de9498ab88b048`

3.2 is a bounded accepted clarification, reviewed and adjudicated separately: the keyless staging Graphiti startup mechanism in AC-07, and the compatibility correction excluding the pinned keyless baseline from the legacy clear/re-projection journey. Nothing else in 3.1 changed.

## Problem and outcome

Feature PRs land on `staging`, whose Railway deployment is the URL used to validate a candidate. `main` is a production release pointer: it advances only to an explicitly validated, annotated `vX.Y.Z` tag by fast-forward. Staging periodically receives sanitized production Postgres and the graph already extracted in production, without paying to extract it again. Emergency direct-main changes are exceptional, authorized, and attributable.

This PR supplies executable software, tests, configuration validation and activation instructions. It does not merge, deploy, change remote protection or Railway configuration, publish tags, copy live data, or activate a schedule. AIO-1124/1126/1133 remain separate related records, not separate writers of this change.

### Current evidence

- `scripts/branches.mjs` already makes `staging` the contribution/integration branch and `main` the release branch. Preserve those names.
- `.github/workflows/release-candidate.yml` and `scripts/release-candidate-guard.mjs` validate tag identity/version/ancestry/integration reachability but do not attest a deployed candidate or human validation.
- Read-only inspection on 2026-09-07 found `main.enforce_admins=true`, nine existing required contexts, no required Release candidate gate, a required-PR rule, and no observed PR bypass allowance. The older claim that an admin bypasses every check is stale; the present configuration can instead block legitimate fast-forward promotion. Validation must inspect current remote state rather than assume either condition. A subsequent read found main at `9888c93e` (including main-only #691/#692/#695), staging still at the recorded base: ancestry reconciliation is an activation prerequisite through a reviewed PR, not a merge performed by this task.
- `scripts/staging-refresh.sh` restores Postgres only, excludes `graph_episodes`, and excludes reversible secret tables before dump. Its URL/marker/libpq environment defenses are valuable and stay intact for this legacy mode.
- `docs/design/staging-graph-copy.md` was declined because a production runner would have both environments' writable graph credentials, no actual runner was supplied, and staging had no configured graph consumer. `docs/design/staging-graph-reset.md` and #693 deliberately shipped only the manual clear runbook. Do not revive a two-endpoint copier, unauthenticated `/clear` automation, or a remote-shell runner.
- `instrumentation.ts`, `lib/graph/run.ts`, `lib/graph/graphiti-client.ts` show why disabling pollers alone does not prevent manual extraction. `lib/graph/neo4j.ts` has a lossy plain-value conversion unsuitable for lossless graph copying.
- Postgres owns item identity/access, membership, partition pointers and projection ledger (`postgres/schema.sql`, `graph_episodes`, migrations); Neo4j owns extracted entities/facts/episodes. Graphiti is an asynchronous writer. `lib/graph/episode-lookup.ts` matches chunk episodes by item stem plus group. Existing graph tier tests use real Neo4j, not Graphiti.

## Decisions and scope

The default copy is an **online capture interval**, not an atomic point-in-time snapshot across two databases. Postgres uses its normal consistent dump snapshot; graph export reads existing records while production keeps working. Both artifacts belong to one immutable run. Cross-store checks reject an unusable bundle, and a later scheduled run retries. This meets production-shaped testing without a production maintenance window. It does not claim transactionally simultaneous source state. Strict paired point-in-time backup is outside scope unless separately requested. The safe graph sanitation exclusions below are intentional, measured output differences, not a claim of an exact graph clone.

Use two isolated roles: a production-local **exporter** reads production and publishes an encrypted bundle; a staging-local **importer** reads the bundle and writes only staging. Neither holds the other environment's database credentials. Both are separate operational processes, absent from the serving app and its image startup chain. No public Neo4j/Graphiti proxy, no `railway ssh`, no production-to-staging database connection. Ship the two runner entrypoints, role-specific Docker image/configuration, Railway staging maintenance adapter and a reproducible local two-environment harness. Only provisioning the supplied configuration and secrets is deferred; no adapter design or implementation is deferred.

Default schedule is weekly, with manual dispatch using the same entrypoint. The schedule is inert until explicit enablement and successful preflight. One bounded retry per transient capture/transport failure; the next scheduled run is the backstop. Run time and archive-size ceilings must be configurable and have finite defaults. No automatic spending fallback when copying fails.

## Acceptance criteria

The automated and operator outcomes in AC-01 through AC-08 are mandatory. `npm run lint`, `npm run typecheck`, `npm run check:docs` and the required test tiers must exit 0; unavailable verification is recorded as unverified.

- AC-01: a candidate is healthy at the staging URL and environment/source configuration passes preflight.
- AC-02: validation evidence binds the exact annotated tag, commit and deployed instance.
- AC-03: main rejects unvalidated normal pushes; controlled promotion is non-force and emergency changes are audited.
- AC-04: each transport role can access only its environment and authenticated private bundles.
- AC-05: copied Postgres has no usable production credentials and the graph preserves identities/types/access without extraction.
- AC-06: concurrent/failed refreshes cannot expose partial data, and verified rollback restores the prior pair.
- AC-07: all copied-staging graph mutation paths emit zero extraction requests, including manual triggers.
- AC-08: required executable tests pass; live activation is separately evidenced.

### AC-01 — integration deploy and health

Configuration preflight verifies repository/default/contribution branch `staging`, staging service source branch `staging`, production source branch `main`, distinct pinned environment/service/Postgres/Neo4j identities, internal graph hosts and per-environment Railway variable references. Missing/mismatched facts fail with redacted actionable errors. No automatic mutation by preflight. The staging-side verifier never fetches production variable values; it compares pinned IDs and exporter-signed secret/configuration fingerprints and reference descriptions. Production exporter gathers only its own facts; diagnostics contain no secret values.

Add or reuse a lightweight application health endpoint and configure Railway's app healthcheck to it (120-second deployment timeout, bounded per-probe database timeout). Because `railway.json` is shared, this changes production readiness on its next authorized release too; test production defaults. Return healthy only after a bounded Postgres probe succeeds; expose no secrets or data. Candidate validation additionally checks the deployment's recorded commit equals the tag commit. A separate staging-only health-token header (environment secret, absent from all copied tables) authorizes bounded internal Postgres/Neo4j checks and returns ready refresh run ID and graph mode, without returning graph content. In `copy-ready` mode it proves internal graph reads succeed; a generic 200 or `/login` page is insufficient. A feature merge must be observable at the staging URL after activation.

### AC-02 — exact candidate validation

Provide one manual release-controller workflow/CLI entrypoint accepting an exact annotated `vX.Y.Z` tag, staging deployment identity and explicit validation notes. It resolves immutable tag object and commit, runs the existing candidate guard, verifies required CI succeeded on **that commit**, verifies Railway reports a successful staging deployment of the same commit, and verifies health at the pinned staging origin without following off-origin redirects. A protected GitHub environment requires an authorized human's explicit candidate validation before promotion. Validation evidence binds the exact commit, declared mode and deployed refresh run ID. `legacy-pg-only` is an explicit transitional result: ordinary code validation may pass only when the operator explicitly selects that mode and the audit records graph validation NOT PERFORMED. It never emits the full `copy-ready` verdict, never satisfies paired-refresh acceptance, and cannot be silently selected after a copy failure. Once copying is activated, normal controller policy requires `copy-ready`; journal absent/failed/importing cannot downgrade it. The stable health token survives refresh because it lives in staging environment secrets, not `api_keys`. Empty notes, unknown deployment, failed/pending checks, moved tag, wrong commit or unhealthy staging refuse.

The workflow is dispatch-only; the protected environment deployment-branch policy permits exactly `staging`, with required reviewers and self-review prevention. Controller checkout uses the dispatch SHA on that branch, never the candidate tree, and workflow/code ownership requires review. Environment-scoped App keys are unavailable to other refs/events. `GITHUB_TOKEN` remains contents-read-only: a short-lived installation token with checks-write publishes `Staging candidate validation` explicitly on the candidate SHA; the same normal release App has narrowly restricted contents-write for promotion. Keep the existing workflow-permissions guard intact and add guard coverage for this environment/App-token wiring, trusted checkout and absence of candidate execution.

Staging may advance after validation: the immutable candidate deployment evidence remains usable only if its recorded deployment was actually validated; the workflow must never replace that evidence with 'current staging is healthy'. If deployment metadata no longer proves the candidate identity, refuse and validate the candidate again. No untrusted PR artifact or candidate executable is run with release credentials; controller code comes from the trusted protected branch. Record actor, workflow run, tag object, commit, deployment URL/ID and notes in a durable GitHub audit artifact/check linked from the release operation.

### AC-03 — enforceable promotion and emergency path

After successful main push, the controller observes the production deployment until it reports the same SHA and healthy status or a finite deadline expires. Report promoted-but-deployment-unverified/failed separately; never undo main or re-push blindly to repair a webhook.

Promotion re-fetches refs and rechecks tag object, required checks, deployment evidence and current `main` ancestry immediately before a non-force push of the exact peeled commit to `main`. Use an environment-scoped GitHub App installation credential so downstream Railway automation is triggered. One repository-wide promotion concurrency group covers ordinary and emergency operations; duplicate promotion of the same main SHA is an audited no-op. If main advanced incompatibly, fail; do not merge/rebase/create a replacement candidate.

Supply declarative GitHub rulesets and a read-only **effective-policy** verifier. The target is three active branch rulesets, each matching exactly main, with bypass sets separated by capability:

| Ruleset | Rules | Bypass actors (always mode) |
|---|---|---|
| `main-integrity` | Block non-fast-forward updates and deletion | None, including no admin-role bypass |
| `main-release-evidence` | All nine currently required CI contexts plus Release candidate gate and Staging candidate validation; each pinned to its measured producer integration ID | Emergency App only |
| `main-release-writer` | Restrict updates and require a pull request | Normal release App and Emergency App only |

Normal App bypasses writer/PR restrictions, NOT checks or integrity. Emergency App bypasses writer/PR/check restrictions, NOT integrity. Every other actor, including normal repository admins, is denied direct updates and PR merges to main by restrict-updates even if every check is green. Do not use 'pull-request-only' bypass mode for these Apps because they must push a fast-forward directly. Do not add require-linear-history: fast-forwarding may validly include merged staging history. [GitHub documents restrict-updates, per-ruleset bypasses and producer-pinned checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets); [applicable rulesets and classic protection all layer](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets).

Activation installs/verifies the active rulesets FIRST while existing classic checks still protect main, then removes redundant classic required-status-check and required-PR constraints that would prevent the two Apps' intended bypass. Preserve the same CI requirement set in `main-release-evidence` throughout; this is migration of enforcement, not removal of checks. Classic integrity constraints may remain with enforce_admins=true, but classic required-check/PR constraints must be absent in the final profile. The verifier inspects all applicable repo/org rulesets plus classic protection, refuses evaluate/disabled enforcement, unexpected admin/team bypasses, missing producer IDs, actor mismatches, missing checks or conflicting classic constraints. Test the actor×operation matrix on a disposable protected branch: human/admin direct push AND PR merge fail; normal actor wrong/pending-check update fails; emergency missing-check non-force update succeeds with authorized controller evidence; neither App can force-push/delete. Repo owners retain the administrative ability to edit policy, which is a separate audited administrative action, not an update bypass.

Require live main ancestry as well; main-only changes are reconciled through a separately authorized reviewed PR. Cancelled/superseded staging CI is a missing-evidence refusal with exact-SHA rerun/latest-completed-tip remedy. Protected release environments require reviewers/self-review restriction and protected controller-workflow ownership. A host that lacks the documented ruleset capabilities is NOT ready; do not fall back to enforce_admins=false. No remote policy mutation occurs in this PR task.

Emergency direct-main mode is a separate protected environment and separately scoped break-glass actor, disabled unless configured. Require incident/issue URL, concrete reason and human authorization, preserve non-force ancestry, log before attempting the update and record resulting SHA or refusal afterward. The emergency App is explicitly permitted to bypass required checks/PR restrictions for a non-force hotfix (otherwise an unstaged, untagged emergency could not work). Its deliberately broader exception must never be available through ordinary promotion inputs or credentials. An emergency invalidates pending ordinary promotion evidence when main ancestry no longer holds; reconcile main back to staging through normal reviewed PRs. Audit provider events for out-of-controller direct-main pushes and fail/alert loudly rather than describe them as authorized releases. After an emergency, main may temporarily be untagged; the audit states that exception. Back-merge through a reviewed staging PR, then validate/tag/promote a new release to restore the normal pointer invariant; never retroactively label the emergency validated. Repo admins can ultimately change policy; this is governed administrative access, not an impossible promise that a repository owner cannot override GitHub.

### AC-04 — safe executable transport

Provide separate export/import commands and role-specific runner configuration examples with secret names only. Exporter has production PG read-only dump identity, production-internal graph access and write-only access to its private bundle prefix; importer has read-only access to that prefix and staging-only DB identities. Encrypt in transit and at rest; sign the canonical manifest and ciphertext digest with an exporter-only Ed25519 private key, verified against a pinned exporter public key. Encrypt payload with AES-256-GCM under a random per-run key sealed to the importer public key (standard audited sealed-key primitive, not custom cryptography); exporter never holds importer private key. Verify signature before decrypt/import. Shared AEAD possession alone is not publisher authenticity. Credential comparison uses HMAC-SHA-256 with a dedicated random comparison key shared only by the two ops roles (never the app), a versioned key ID and domain separation for each credential class. Both roles compute over the same normalized credential bytes; compare without printing values. The comparison key is distinct from signing/encryption keys and absent from manifests/logs. A plain password hash or a salt unknown to the importer is not a valid comparison mechanism. Do not publish data in GitHub artifacts/logs. Use restrictive temporary-file permissions and cleanup on success/error; export-prefix retention defaults to fourteen days and is independent of rollback. The importer copies the verified bundle into its OWN private durable rollback store before accepting it as ready. Source storage remains importer-read-only; exporter cannot read/write the staging rollback store. The staging store keeps the current known-good pair without TTL, plus the previous pair while a replacement is in progress; remove the old pair only after the new pair is healthy, durably pinned and read-back verified. No shared publisher key or source-prefix acknowledgement channel is needed. Redact credentials and connection strings in errors.

Community Neo4j's READ session is not an authorization boundary. Explicitly require distinct credentials across environments and runner network isolation; the exporter has fixed read-only queries and no target connection/import code path. Test no mutation Cypher is emitted by the export execution path. Staging importer verifies pinned Railway environment ID, service/database identities and internal parsed host allowlist; `staging_marker` alone is insufficient. Refuse missing IDs, production environment, host aliases/redirect/routing parameter evasions, shared credentials, unknown identity and unsupported schema before a target write. The supplied harness proves exporter cannot reach staging databases and importer cannot reach production databases. Live network/identity checks are rollout evidence, not local-test substitutes.

### AC-05 — sanitized Postgres and graph bundle

Extend the refresh policy with a separate paired-bundle mode; preserve legacy PG-only behavior and its explicit warning. Paired mode includes `graph_episodes` and all partition/pointer/access state. Continue excluding ciphertext tables and transitive FK dependents before data can leave the exporter. Also remove usable authentication material: API/agent keys, magic/invite tokens and password hashes; verify already-distinct staging-only AUTH_SECRET/SECRETS_KEY through fingerprints (do not rotate them on refresh) and provision designated staging testers through existing admin tooling. Preserve member IDs, posture, group membership and source ownership. Staging credentials come from its own secret source, never the production dump. Each import reapplies explicitly allowlisted tester passwords/API credentials from staging-only secrets through the existing admin writer before startup; verify matching member identities/postures and do not grant additional access. A missing tester credential is a failed readiness check, not an instruction to reuse production credentials. Enumerate all credential-bearing tables/columns from current schema and migrations, with an explicit policy/test for each. Sanitation occurs at export: keep one read-only repeatable-read Postgres transaction open, export its snapshot, pass that snapshot to pg_dump for `public` schema and retained tables, and use explicit column projections/COPY for transformed tables from the same snapshot. Exclude transformed table data from the dump, restore its projected data before post-data FK constraints. No unsanitized full scratch restore and no additional production Postgres service. A sanitizer validation failure discards the private temporary artifacts; no bundle is published.

Credential/data policy for paired mode (legacy mode remains explicitly separate):

| Data | Export policy |
|---|---|
| `auth_users` | Keep identity/email; password_hash NULL |
| `auth_tokens`, `oauth_states`, `api_keys`, `agent_tokens` | Exclude table data |
| `integrations`, `member_secrets` | Exclude table data |
| `gateway_service_identities`, `gateway_service_credentials`, `gateway_connections`, `gateway_resolution_leases`, `gateway_executions`, `gateway_approvals`, `gateway_audit_log` | Exclude table data and full transitive FK dependent closure |
| `social_jobs`, `llm_usage`, `llm_failures`, `usage_costs` | Exclude data: no replay queue and no production spend attributed to staging |
| `graph_episodes` | Include current ledger; sanitize completed pending-delete metadata as specified below, retain pending/deferred current projections truthfully |
| `arc_cache`, `work_timeline_cache` | Exclude generated caches; avoid stale derivative content across sanitation |
| All other source/ownership/access rows | Keep unchanged, subject to FK closure and sanitation validation |

Check schema and migrations for every `*_hash`, `*_ciphertext` and equivalent authentication field. Explicit classifications include credential hashes above and `gateway_resolution_leases.lease_hash`; noncredential `content_sha256`, `facts_hash`, `request_hash`, `request_envelope_hash` are not globally erased. Add a checked-in classification map with a failing unknown-column guard, including credential fields that do not use those suffixes. Queue tables that acquire outbound behavior require an explicit exclusion/classification test.

'Sanitized' means credentials and outbound integration capability removed; source documents, names, emails and graph prose remain real organizational data, available only to authorized staging testers under existing tier controls. This is not anonymization. Existing pending outbox/jobs capable of outbound action are excluded at export; retain referential integrity and document the exact policy.

Graph export copies existing node labels/properties, relationship types/properties/endpoints, UUIDs, episode names, group IDs, embeddings and temporal values without LLM calls. Use a versioned typed codec preserving Neo4j integers beyond JS safe range, date/time/duration/point/byte values and arrays; reject unsupported types/schema, never silently coerce. Stable export-local node identities reconnect relationships; never equate UUID uniqueness across groups. Retain indexes/constraints required by the pinned graph version, recreated from an allowlisted compatible schema rather than executing arbitrary bundle Cypher. Fixed parameterized statements only; identifiers validated/escaped from the supported schema.

Run an export `--census` dry run before activation: return label/relationship-type/episode-name-pattern counts and unsupported shapes, never raw content. Supported source mappings are `items:<uuid>[#chunk]` via copied items + graph_episodes and exact group/partition ownership; `correction:<arc_id>` via copied `arc_corrections`, team and exact stored synthesis scope (including explicitly validated legacy tier scope). An unresolved/ambiguous correction does not inherit a group merely because its string resembles one. Unknown types/names are an actionable named refusal, not an operator instruction to delete production data.

Sanitation is explicit and conservative. Exclude episodes belonging to the ledger's **old pending-delete group**, or to deleted/inaccessible sources, retaining safe current-group episodes. A fact whose provenance contains ANY excluded/unresolved episode is excluded as a WHOLE: do not remove a provenance ID and retain blended fact prose. Empty-provenance facts are excluded because no source-tier proof exists. Retain only entities supported by retained episodes/facts; clear their derived summary cache, and omit `Community` nodes and their membership/summary/embedding caches entirely because group membership alone does not prove source provenance. Preserve supported Entity names, IDs, labels, embedding values, retained facts and current episode content/types; no regeneration occurs. Declare these exclusions in manifest sanitation counts, separate from transport errors. This copies the usable extracted graph, not unsafe derived caches or pending deletions. No silent fallback to re-extraction.

Pending/deferred CURRENT ledger rows remain pending/deferred, not falsely confirmed. Clear old pending-delete metadata only when every old-group episode/fact has been removed by sanitation; this is import sanitation, not a production ledger write. Nonpending UUID/chunk identity must exist in the sanitized graph; mismatch of a current record that should have been retained refuses the bundle rather than silently discarding it. Item/access partition mapping is validated against copied Postgres for every retained episode and fact, not merely existing ledger rows. Fact endpoints must exist, their groups must agree, and every provenance episode must be retained in the same authorized group. Source changes may make the capture unusable: reject and retry the whole capture. Manifest capture start/end plus counts describe the interval, never an atomic timestamp.

Validate checksums, codec/schema versions, preserved property types, sanitation counts and graph/ledger relationships before publish and again after import. Tests include a mixed-source fact and community/entity summary containing an excluded source, proving that removing a provenance link does not retain sensitive derivative text.

### AC-06 — refresh concurrency, failure and rollback

Ship both Docker-harness and Railway supervisor adapters behind the same bounded interface; no adapter implementation is deferred. The new Railway maintenance module listed below is the single owner of the staging lifecycle API. It uses only a **staging-environment project token**, authenticating with Project-Access-Token, and first queries `projectToken { projectId environmentId }`; account/workspace tokens and wrong/missing environment fail. Pin project, environment and permitted app/Graphiti service IDs; no database-service lifecycle mutation. Supported app operations are documented `deploymentStop`/`deploymentCancel` and `serviceInstanceDeployV2` with an exact staging commitSha. Default copy mode keeps Graphiti stopped because direct Neo4j reads need no sidecar. If optional query mode was explicitly enabled, restore the recorded built Graphiti deployment through the supported deployment restart/redeploy operation, and verify that the resulting build/image identity matches the recorded one; never silently rebuild Graphiti from a moving source branch. Read actual source/image configuration at activation; historical reviewer memory is not evidence of current configuration. Ship concrete GraphQL documents and API fixture tests; schema introspection at preflight checks compatibility, not a deferred design decision. Read-back identifies every deployment before mutation and verifies stop/success afterward. Unknown mutation result is reconciled by read-back before retry.

This PR proposes an explicit narrow policy amendment in the operating docs: the activated, reviewed staging-maintenance controller alone may stop/cancel/restart the two pinned staging services to replace/roll back copied data and catch up to the staging branch head. It does not permit agent CLI lifecycle commands, `railway ssh`, source mutations, production lifecycle APIs, arbitrary branch/commit deployments or generic GraphQL. Current task invokes none of these. Production remains branch-driven only. Guard the single API owner and callers, and require explicit activation/configuration for the controller; this is a visible policy change, not an API workaround for the CLI ban.

Whole-graph replacement is an explicit destructive operation, permitted only on the **pinned staging Neo4j database** by the importer. New file: scripts/staging-ops/neo4j-replace.mjs owns bounded batches of whole-graph node/relationship deletion and typed replay, including rollback. Before the first delete and before every retry, require importer environment ID equals the pinned staging ID; its project token confirms the same environment; parsed internal host/service identity and selected Neo4j database match the recorded staging target; graph credential fingerprint differs from the exporter-signed production graph fingerprint; coordinator-election AND exclusive data-use locks are held; and all staging app/Graphiti deployments have been read-back verified stopped. A Postgres marker alone never authorizes graph deletion. Refuse routing aliases/unknown database identity and wrong graph credentials before mutation. The graph deletion module is unreachable from exporter/app/lib; extend the whole-graph-unreachability guard to destructive Cypher patterns and allowed ownership, with real execution spies proving exporter emits no write and wrong-target importer emits no delete. Preserve existing human-only `/clear` owner/guard; no new `/clear` caller. The narrow maintenance policy explicitly includes this staging-only replacement, not a generic graph-wipe permission.

Postgres replacement has the same target-identity standard. Runner admission parses exactly one
`postgres`/`postgresql` URL with an explicit internal host, port and database; only documented
non-routing connection options are accepted, with duplicate, unknown, multihost, socket, service,
host/hostaddr, database and credential overrides refused. Node and every `pg_dump`/`pg_restore`/
`psql` child consume a reconstructed canonical URL while libpq routing environment variables are
scrubbed. Before drain, during first bootstrap even when no marker exists, and immediately before a
restore, the environment-scoped project token must read back the pinned Postgres service instance,
active deployment and private endpoint plus the active importer deployment's current/deployed
`DATABASE_URL` and exact Railway service reference. The lock-owning live session must report the
same configured host/user/database and live database/server port. Equal private DNS names and global
service IDs across distinct Railway environments remain valid; the environment/service-instance
tuple, not string inequality, provides isolation. A marker alone never supplies this proof.

Create dedicated `staging_ops` schema/journal only through the ops installer, never normal schema/migrations; source dumps use public only, preserving control state through `pg_restore --clean`. Two session advisory locks on dedicated PG connections: coordinator-election exclusive lock for the full run, and data-use shared/exclusive lock. A journal timeout never steals a live lock. Record `capturing → published → draining → importing → verifying → booting → ready`, plus `failed` with last safe checkpoint. Status/journal survives worker crash. A new worker must acquire election lock and reconcile the journal/platform state before resuming.

The **actual fence** ships in schema loader and both staging startup wrappers. Before app startup, the supervisor checks the journal and acquires the shared data-use lock, rechecks state, then keeps that connection alive for the entire child Next process lifetime; lock loss kills the child fail-closed. This prevents startup TOCTOU. The loader holds the shared data-use lock for its whole migration; importer invokes loader on the same exclusive-lock-owning client via explicit injected connection, never an env/PID bypass. Production defaults follow their current path. Missing control schema fails closed only after copy-mode activation. Graphiti is stopped and query-only/uncredentialed for mutation, with its fixed deployment observed by the controller. All staging instances must run the fence-capable baseline before activation.

The bundle records source application commit, canonical database-schema fingerprint and the deployed source build's migration-set identity (hash of schema.sql plus ordered migration paths/content hashes). This is declared build identity, not a fabricated applied-migrations ledger. Source health/build metadata supplies that identity; absent/unknown identity refuses. Before draining, the pinned importer must prove its loader manifest is compatible with that source identity; default is exact equality, with any supported upgrade path explicitly versioned and tested. Older/unknown/incompatible loader sets refuse while staging keeps serving, naming the required separately authorized runner-image upgrade. Never replay an older loader and hope later app preDeploy repairs it.

Before **every** ordinary import may enter draining, verify the staging-owned prior pair exists in durable storage, can be read/decrypted, has valid manifest/checksums/codec and contains the recorded last-ready code/mode/schema metadata. Expired, absent or corrupt prior pair refuses while the current app remains serving. Prior pair means the last installed ready dataset, not preservation of every later disposable staging edit.

First import has no last-ready record. Ship explicit `bootstrap-rollback` command, used once before scheduling: stop/drain staging with the same identity/fence checks, capture BOTH existing staging stores and current deployment/mode as a staging-owned rollback checkpoint, verify it durably, then restart the unchanged deployment. This bootstrap performs no destructive DB write; if backup fails, restart unchanged stores and refuse initial import. A legacy PG-only baseline can be backed up with its graph-disabled mode and restored as legacy, never relabeled copy-ready. Initial bootstrap checkpoint is sealed/authenticated under importer-owned backup credentials, accepted only as rollback—not as an exporter-signed source bundle. No empty/assumed first-import exemption. These backup files may contain existing staging credentials and remain private to staging. Tests cover first-import backup failure and expired source objects after successful local pinning. A full bootstrap checkpoint restores the existing staging authentication state captured in that checkpoint; its member identities need not match the configured testers for incoming source data. Credential preservation applies only to a validated, importer-authenticated staging rollback checkpoint with `databaseMode: full`. It does not authorize a source bundle to retain credentials, create missing tester identities, or widen access. For a full authenticated staging rollback checkpoint, legacy mode means graph use remains disabled; it does not require the captured stores to be empty. Restore and verify both captured stores, including any existing graph and ledger contents, without asserting copy-ready correspondence or granting copy-ready validation. The empty-graph/manual-clear requirement applies to legacy PG-only refresh, not restoration of a full staging-owned checkpoint.

Refresh acquires election lock, sets `draining` (new starts/predeploys refuse), stops/cancels all pinned staging app and Graphiti deployments and verifies none remain serving, then acquires exclusive data-use lock. Existing starts holding shared lock therefore cannot overlap restore. Keep the verified staging-owned prior pair, pin the incoming signed bundle in staging durable storage as a candidate without overwriting last-ready, install the new pair, migrate, validate, and record `booting` with the selected verified commit before releasing the exclusive data lock. Start fresh processes through the adapter and healthcheck; atomically advance the journal last-ready pointer and mark `ready` only after health succeeds AND the candidate rollback copy has been read-back verified durable. Until then keep the prior pointer and pair. Paired Postgres restore is section-wise (schema, retained/projected data, post-data constraints), not the legacy script's single pg_restore transaction. The stopped-app/exclusive-lock fence plus two-store rollback replaces that guarantee; do not pretend a COPY between restore commands is one transaction. Staging has an intentional maintenance window; production remains online. A crash never turns `importing` into `ready` by elapsed time. Rollback repeats drain/stop/exclusive-lock and the same installation sequence for BOTH prior stores: compatibility check, schema replay, credential handling appropriate to the authenticated checkpoint type, verification, booting journal with the recorded last-ready commit/mode, then restart/health. Sanitized source installs and sanitized staging rollback checkpoints require staging-only allowlisted tester-credential reapply through the existing admin writer. Reapply uses explicit configured staging-only secrets and verifies every configured tester’s existing identity, active status, role and posture; missing or mismatched identities or credentials refuse. It does not prompt a human, mint unconfigured access, or recover production keys. A full importer-authenticated staging rollback checkpoint restores its captured staging credentials unchanged and does not apply incoming-source tester configuration to the restored baseline. This exception is selected by verified rollback provenance and full database mode, never by a legacy declaration or a caught tester-validation failure. An incompatible prior loader or failed required verification refuses safe startup; failed rollback stays stopped and reports recovery required. Staging API/health refuses candidate validation until ready. Fresh processes discard warm arc caches; a separate process cannot evict them.

After import, deploy the latest observed staging branch head rather than blindly restarting the pre-refresh app. Main-only changes are not merged by the controller. A push whose predeploy failed during maintenance is not lost: persist a catch-up target in the journal; compare branch head against served SHA again after ready, deploy the newer staging head when needed. The lightweight importer runner also retries an outstanding catch-up every five minutes independently of the weekly data schedule, with bounded attempts/backoff and loud failure status; rapid new merges may supersede the target but never silently mark it deployed. Idempotent retry uses the original bundle ID, not mutable latest. Runtime activation requires the provided journal/fence/controller setup, no human 'stopped=true' claim.

Official API contracts: [Railway token scope](https://docs.railway.com/integrations/api), [deployment lifecycle](https://docs.railway.com/integrations/api/manage-deployments), [exact-commit service deploy](https://docs.railway.com/integrations/api/manage-services). Checked read-only during design; no live lifecycle calls.

### AC-07 — zero extraction and outbound isolation

Copied staging has an explicit runtime copy/read-only graph mode. Disable ingestion/social/background pollers and graph projection by policy, even if an environment flag accidentally enables one. Gate all graph mutation entrypoints including manual/admin projection, reconcile/delete, correction episodes and any direct Graphiti mutation before network I/O; direct graph reads remain available; model-dependent search follows the explicit policy below. Preserve existing production behavior and bounded-projection legacy mode. Mode detection must fail closed for the pinned staging deployment or a restored staging marker; do not depend solely on an operator-renamable environment name. A missing/failed mode check cannot enable writes.

Staging Graphiti must have no direct provider credentials; the existing brain graph-proxy chat and embedding endpoints refuse copy mode by default before resolving a provider key. Keep the graph-client mutation gate as the independent first layer. No new proxy service is necessary. Query-only credentials, if graph search requires embedding/reranking, are staging-scoped and explicitly separate from extraction. Do not assume allowing embeddings while denying chat makes every Graphiti search work: the pinned search recipe may invoke a chat reranker. Place the default-no-spend policy at shared key resolution (`resolveAnsweringKeys` and `getProviderKey`) and guard the sanctioned raw transports (`lib/llm/complete.ts`, `lib/query/claude.ts`, `lib/chat/title.ts`) plus embedding/image transports; per-feature flags alone are insufficient. Default copied staging supports direct Neo4j graph-backed reads and FTS, with model-dependent search/answering explicitly disabled. Optional separately budgeted interactive queries may enable only a verified nonextracting recipe; test the pinned protocol and do not allow arbitrary graph-proxy chat bodies based on a claimed caller purpose. Graphiti mutation routes are unreachable from the app through the allowed transport, and the sidecar has no independent provider fallback. No new `/clear` caller. Production-level SMTP/Resend/Sentry/outbound connector/provider credentials fail preflight. No model invocation is enabled by default: answering, arc synthesis, timeline summaries, meeting extraction, social/image jobs and graph reranking/embedding all short-circuit under the central staging spend policy. Optional explicit staging budgets may enable on-demand answering (and then only identified query-only graph recipes), never background extraction. Copied generated caches are removed, so cache expiry cannot silently trigger a model. `llm_usage`/`usage_costs` start empty in staging; 'zero extraction' does not mean every interactive LLM answer is free.

#### Keyless staging Graphiti — the missing startup mechanism (AIO-997 clarification, accepted 2026-09-09)

This is a bounded material clarification of the zero-spend/key-absence requirement already accepted above, not a new feature and not a relaxation of provider-credential preflight. It exists because the requirement as written was not satisfiable: the upstream server's `Settings` declares `openai_api_key: str` with no default and its lifespan constructs `ZepGraphiti`/`OpenAIGenericClient`, so removing staging's provider key prevents startup — while the same contract requires a successfully deployed pinned sidecar. App-only no-spend gating does not remove a separate Graphiti provider key, and neither a fake key nor a guessed proxy is an acceptable reconciliation.

Staging Graphiti has an explicit keyless no-model serving mode selected by its matching pinned staging environment identity. In this mode the sidecar starts and serves its existing `/healthcheck` endpoint without constructing Graphiti, OpenAI/other provider clients, database initialization, extraction workers or model transports. Health reports process availability and the no-model mode; it does not claim graph/database readiness. All non-health service operations refuse before route dependencies, request processing, queue insertion or outbound work. The app's copied graph reads continue through the existing direct Neo4j/FTS paths; Graphiti search, embedding, extraction and mutation are unavailable. No direct provider credential or fabricated substitute is provisioned. Outside explicit staging scope the existing Graphiti application, initialization, routes and production behavior remain unchanged. Invalid or contradictory staging identity fails startup instead of falling through to the production application. The configured staging launch command must execute this reviewed mode selection; a provider start-command override may not bypass it.

Scope selection uses the existing `STAGING_OPS_ENVIRONMENT_ID` and `RAILWAY_ENVIRONMENT_ID`; no new enable flag and no environment-name guessing. Railway supplies an actual environment ID on every deployment, so its presence alone never selects staging.

| Pin | Actual environment | Mode declaration / claim | Selection |
| -- | -- | -- | -- |
| Absent | Any/absent | Absent or legacy-pg-only, no copy claim | Original production application unchanged; legacy declaration alone does not enable keyless mode. |
| Absent | Any/absent | Copy claim | Startup refusal. |
| Nonempty | Absent or different | Any | Startup refusal. |
| Nonempty | Exact match | Absent, legacy-pg-only or copy-ready (either activation flag) | Keyless staging app. |
| Nonempty | Exact match | Unknown nonempty mode | Startup refusal. |
| Absent | Any/absent | Unknown nonempty mode, no copy claim | Original application unchanged; no new global production environment validation. |

"Copy claim" means declared `copy-ready` or `STAGING_COPY_MODE_ACTIVATED=true`; "no pin" includes absent, empty and whitespace. Explicit `legacy-pg-only` is preserved inside pinned staging scope so the sidecar can be commissioned before bootstrap. Selection is a pure function that imports neither FastAPI nor the production modules, so the matrix is testable without image dependencies.

Implementation is one image-local entry module (`graphiti/staging-entry.py`, copied to `/app/graph_service/staging_entry.py`) which the image CMD targets. On the ordinary branch it re-exports `graph_service.main.app` unchanged; on the pinned staging branch it constructs a minimal FastAPI app (`docs_url`/`redoc_url`/`openapi_url` all `None`) and never imports production main, the ingest/retrieve routers, `zep_graphiti`, `graphiti_core`, `openai` or `neo4j`. Health keeps HTTP 200 and `status: healthy` and adds `mode: staging-no-model`, a human/commissioning readback rather than a new machine consumer. `GET`/`HEAD` health are served; every other path and method — including upstream's `POST /messages`, `/entity-node`, `/clear`, `/search`, `/get-memory`, `DELETE /entity-edge`, `/group`, `/episode`, `GET /entity-edge`, `/episodes`, the documentation surfaces and anything undefined — receives a stable named `403 staging_graphiti_no_model` by default deny. No empty 200 search result and no accepted job. No app routes, Neo4j queries, schema, importer protocol or provider adapter change is required, and no `/clear` caller is added.

Evidence is behavioural against an actual freshly built image, not a source-text guard: `graphiti/verify-staging-entry.py` gates the build, and `graphiti/staging-keyless-diagnostic.py` (run by `graphiti/keyless-image-check.sh`, network disabled) proves health, the enumerated refusals, clean shutdown, refusal before the production application is imported, delegation identity for the unpinned case, and the preserved unpinned missing-key startup failure. A test-only mounted socket/module tripwire records and refuses outbound connect attempts in the server process, because a disabled network proves only that no outbound call *succeeded*; no test hook and no dummy key ships in the image.

Consequences stated rather than assumed: Graphiti HTTP search remains unavailable, so retrieval's best-effort Graphiti leg yields no graph facts and `/api/v1/graph-query` may return 502 when configured and scoped (503 when the URL is absent). "Direct Neo4j reads unchanged" describes existing direct Neo4j consumers, not conversion of every Graphiti endpoint. Keyless health is a pre-drain commissioning liveness capability, not a promise that Graphiti keeps running after maintenance: the importer's drain stops app and Graphiti, its boot path deploys the app rather than the sidecar, and this correction adds no sidecar restart and no post-bootstrap preflight requirement.

## Activation checklist and compatibility

Ship a runner Dockerfile containing Node and pg_dump/pg_restore/psql pinned to the measured server major (current audit Postgres 18); reuse version refusal and do not assume the app slim image has those clients. Use service names `aios-staging-export`/`aios-staging-import`, satisfying the existing service identity guard. The exporter is a weekly cron service in production private networking; importer is a staging cron service polling encrypted ready bundles/catch-up state every five minutes, importing only a new weekly run. Both run explicitly pinned immutable image digests, with NO repository branch-push deploy trigger. Preflight refuses a source-connected/moving-tag runner or any ordinary autodeploy trigger. Controller never updates its own or exporter images; upgrades are separately authorized maintenance when no worker is active, with journal-format compatibility checked. SIGTERM records an abort/failure checkpoint best-effort and exits without declaring ready. Read alongside the mandatory bounded rollback and durable ready-commit rules in AC-06: observed cancellation prevents a new candidate ready submission; admitted work settles and records its outcome under coordinator ownership. Mandatory recovery uses a fresh bounded scope and may restore the verified prior pair to ready. A ready commit already completed is preserved and reported truthfully. SIGKILL/connection loss is reconciled from durable journal next run. Test interrupted worker replacement independently of ordinary branch merges, which must not replace a runner. Their role-scoped images/config must not inherit the app provider secrets. These are two additional scheduled worker services plus private object storage, justified by isolated source-private reachability and independent target maintenance control; no new database or query-proxy service is required. Compute/storage/egress may add small usage charges; do not claim zero infrastructure cost. Zero duplicate graph extraction is the guarantee.

Before enablement, operator must provision the supplied two isolated runner configurations, private encrypted object storage with separate publish/read identities, distinct graph credentials, source PG read-only role, importer-owned durable rollback storage and verified bootstrap checkpoint, working supervisor/lease integration with staging deploys, tester credentials and query-only graph capability. Run read-only preflight against live identities/variables/branch rules and negative network checks. First refresh is manual; inspect copied counts/credential removal/tier queries/zero extraction and rehearse staging rollback. Only then enable weekly schedule. Configure GitHub checks/environment/release actor and verify negative unauthorized/wrong-SHA pushes on a disposable protected branch before enforcing main. Preserve existing required checks throughout; do not disable admin enforcement to unstick promotion.

No schema changes to production are required merely to hold the operational journal. The coordinator verifies the actual brain work key before writing any AIOS-Work trailer; AIO-997 is a ticket reference, not an invented or assumed brain row key. Do not guess one or equate task completion with staging merge. Any actual application schema changes discovered necessary must follow schema+mirror migration rules and return for spec adjudication. #694's transaction API must be used as shipped, not patched around. Failure to provision any prerequisite is a clearly named NOT ACTIVATED status, not completion of live rollout. Roll back software by disabling schedules/controller and returning to prior staging pair/configuration; do not move main backward or undo one-way production migrations. Legacy PG-only refresh remains available only with its documented empty-graph/manual-clear semantics, never as a silent fallback for paired refresh.

**Compatibility correction (AIO-997, accepted 2026-09-09) — the pinned keyless baseline is excluded from the legacy clear/re-projection journey.** `legacy-pg-only` inside pinned keyless staging scope is a zero-spend commissioning/bootstrap baseline, not permission to run the historical graph-clear-then-re-project sequence. The keyless sidecar deliberately refuses `/clear` and every other graph operation, so those steps cannot run against it; the user's explicit zero-AI requirement takes precedence over the historical availability of legacy re-projection, and re-projection would spend on extraction that this mode exists to avoid. Graph use stays disabled in the PG-only baseline. Do not weaken the sole clear-owner guard (`scripts/staging-graph-clear.mjs`, pinned by `test/guards/graph-clear-unreachable.test.ts`) and do not add a clear caller to reach around the refusal; graph readiness is established by the paired import, not by re-extraction. Existing UNPINNED legacy behaviour and the legacy script are untouched by this correction. A full importer-owned baseline rollback retains both existing stores under its existing protocol and needs no graph clear for that checkpoint. The matching operator instruction is a prominent exception in `docs/OPS.md` §11.

## What would falsify this design

A normal actor can push unvalidated main; a check on another SHA suffices; either runner can mutate the wrong environment; staging accepts production credentials; graph copies change type/identity/tier; a refresh triggers one extraction request; readers observe a partial pair; an interrupted import loses its rollback pair; or docs call live enforcement/automation active before the prerequisites are verified. Each maps to AC-01 through AC-08 and must have direct negative evidence in the acceptance matrix.
