# Phase C — per-project graph projection & migration (design)

**Status:** design, pre-code, **revised after THREE adversarial plan-review rounds** (Fable round 1: 2 Blockers + 5 Highs + 2 Mediums, folded; Fable round 2: BLOCKED — 1 Blocker + 3 Highs + 3 Mediums + 3 Lows, folded — the Blocker being that the first fold's General-remap contradicted the design the governing spec had already ruled; Codex: BLOCKED — 3 Blockers + 4 Highs + 1 Medium, folded — the sharpest being that "the home partition is always included" contradicted the spec's restriction-moves-not-copies rule and would leak restricted facts through General's grandfathered group). Governs the Phase C graph slices (spec `docs/specs/project-context-classification-v1.md` §6 / §17-C). `AIOS-Work: PCCC-2`.
**Gate:** touches schema + LLM extraction cost + multiple surfaces (CLAUDE.md task gate) — reviewed as a plan before any code slice starts. PCCC-3 does not open until the reviewed doc merges.
**Build-with:** fable / high — the code slices this doc governs change the graph's partition key, prod schema, and real LLM spend; each gets its own PR + two-model adversarial review.
**Increment:** one PR, docs only. Every code change is deferred to the sibling slices PCCC-3..7 (§5), each its own ticket + PR + review.

**Access posture (standing, explicit):** DEFAULT-DENY throughout — every enforced read in this design fails CLOSED on error, absence, or ambiguity (an unresolvable scope, a failed substrate read, an unconfirmed purge, an un-latched partition all yield the OMITTED leg / the neutral envelope, never a wider read), and the external tier keeps the §5.8b omit path with the brain-api's 422 rejection contract for tier-violating requests (docs/brain-api.md) unchanged.

## 1. Problem

The Graphiti graph is partitioned by **tier**: an item's episodes live in `<teamSlug>_team` or `<teamSlug>_external` (`lib/graph/project.projectItemsToGraph` → `episodeGroupId(teamSlug, item.access)`), and a reader searches `visibleGroupIds(tier)`. That write-time `item.access` split is the ONLY graph isolation (no RLS).

Phase B enforced the **item** reads at project grain but could not enforce the **graph** legs — the mirrors are tier-partitioned, not project-partitioned. PCCB-2 handled it by **OMITTING the graph legs for any attenuated/partitioned principal under enforcing** (§5.8b): safe but lossy. Phase C re-enables them by partitioning the graph per project (PCCC-1 landed the key scheme `projectGroupId`/`graphGroupIdsForVisibleProjects`).

## 2. Decision

### 2.0 Scope correction from review — TWO invariants the first draft dropped

- **Tier isolation is NOT subsumed by project partitioning (round-1 High 3).** `project_context_memberships` is orthogonal to `items.access`: an initiative project can hold BOTH team- and external-access items, and Graphiti search has no per-fact filter (the whole §5.8b motivation). So a project graph is tier-MIXED. An external-tier principal visible to project P via the External built-in would otherwise read team-tier facts from P's graph. **Decision: Phase C re-enables the per-project graph legs for TEAM-TIER principals only. External-tier principals KEEP the omit path** (as today) — they are a minority (client/consultant collaborators), team-tier principals `canSeeAccess` every access level so a tier-mixed project graph is safe *for them*, and this avoids doubling every partition into `(project, tier)`. Retiring the `_external` tier group is therefore explicitly OUT of Phase C — that group stays live as the external-shared built-in project's partition (§2.4). `projectGroupId` stays tier-free; the tier axis lives in the READ (external → omit), not the key. **And the fan-out set follows from this (round-2 High 3 — the first fold contradicted itself):** ALL of an item's active include memberships fan out, regardless of `items.access` — an external-access item tagged into initiative P lands in P's graph. Project graphs are tier-mixed *by design*; the untag matrix and P̄ count external-access items like any other. Team-tier readers do NOT lose the external-access content they get today from `visibleGroupIds(team) = [_team, _external]`: the external-shared built-in project's partition IS `<teamSlug>_external` by stored pointer (§2.4), so when that project is in their oracle-visible set, its group is in their read set.
- **The content-hash cache must key on `(content_sha, group_id)`, and it does not today (round-1 Blocker 1).** The projector's ledger read is `.eq("source_id", item.id).maybeSingle()` (`project.ts:616-622`) — one row per item — and this adapter's `maybeSingle` returns `rows[0]` SILENTLY on multiple rows (`lib/db/pg/query-builder.ts:336`). So the moment fan-out writes a second row, the projector reads an arbitrary group's ledger; a sha-match against the wrong group SKIPS extraction into a group that never got the content → a **silently-empty project graph**. The per-`(item, group)` ledger read is therefore not an optimization — it is the correctness precondition, and it lands in the SAME slice as the schema.

### 2.1 Schema + projector conflict-target — ONE coupled slice (was "additive"; it is not)

The unique key widens `(team_id, source_table, source_id)` → `+ group_id`. This is **NOT additive** — both projector upserts conflict on the OLD 3-column key (`project.ts:661,893`, emitted verbatim as `ON CONFLICT (…)`), and Postgres requires a unique index exactly matching the conflict target. A single coupled deploy is ALSO wrong (round-2 High 2): `pg:schema` runs as Railway's preDeploy hook (`scripts/pg-load-schema.mjs:7`) while the OLD release still serves, so dropping the narrow unique in the same migration breaks the old code's 3-column `ON CONFLICT` ("no unique or exclusion constraint matching") for the whole deploy window — and **both ledger upserts discard their returned error today** (`project.ts:650, 878-894`), so the failure would be silent: episodes pushed to Graphiti, ledger never written, re-pushed next pass → duplicate episodes; the redaction branch would delete episodes and silently fail to record `pending_delete`. **The sequence is therefore TWO deploys, no broken window in either direction:**

1. **Deploy A (PCCC-3):** migration adds the wide unique as an identically-named `create unique index if not exists … (team_id, source_table, source_id, group_id)` in BOTH the migration and `schema.sql` (round-2 Medium 7 — an inline `unique (…)` mirror in `create table` would auto-name differently and give a from-zero DB two identical arbiter indexes; the narrow unique stays inline at `schema.sql:2382` until Deploy B). Same PR, same deploy: both projector `onConflict` → the 4-column key; the ledger read → ALL of the item's rows (no `maybeSingle` — the adapter's silent `rows[0]` is the Blocker-1 failure mode), split into `currentRow` (matching the target group) and `staleRows`, with Deploy-A semantics `currentRow ?? staleRows[0]` **(as built — reviewed code refines the doc here)**; the change-detection (§2.2); **both upserts destructure and fail LOUD on `{ error }`** (the silent discard above is what would have made every window failure invisible); and an explicit-UPDATE path for the group-move case (a tier flip changes `group_id` on the same logical row — under the 4-column target that's an INSERT of a second row, which the still-standing narrow unique rejects; while it stands, group-move is an UPDATE by the old key). Old code during A's window conflicts on the 3-column target, which still matches the narrow unique — safe. **And the write ORDER inverts (Codex High 4):** today the projector pushes to Graphiti BEFORE writing the ledger (`project.ts:845` then `:878`), and the single-flight is process-local (`run.ts:70-73`) — a deploy overlap runs two instances, so two writers can both read "no ledger row" during a group correction, one inserts, and the other has already pushed episodes into the wrong graph before its insert fails: loud, but the episodes are orphaned with no purge pointer. PCCC-3 therefore **reserves the `(item, group)` ledger row (unlanded) BEFORE the irreversible `addEpisodes` push** — the loser of any cross-instance race fails on the reservation, before anything lands in a graph.
2. **Deploy B (opens PCCC-4):** migration does `alter table graph_episodes drop constraint if exists <narrow unique>` (replay-safe — migrations re-run on every deploy, `postgres/migrations/README.md`) and removes it from `schema.sql`'s `create table`. **The explicit-UPDATE group-move STAYS (amended during PCCC-4 — the first ruling, "relaxes to the plain 4-column upsert", was wrong):** with the narrow gone, a plain upsert on a tier flip INSERTS a new-group row and leaves the OLD-group row live — a mixed multi-row state NOTHING owns until PCCC-5's set-diff machinery exists, with the vacated tier group's content lingering searchable and reconcile/projector each seeing a state the other half-understands (review corrected the first fold's more specific 'sentinel resurrection' mechanism — the certain part is the ownerless mixed state, not the exact resurrection path). One logical home partition = one row, moved in place; multi-row-per-item arrives only with PCCC-5's set-diff, whose removed-side purge machinery is what makes a lingering row safe. Old code during B's window is Deploy A's code (4-column target vs the wide index, move by UPDATE) — safe.

The projector still computes ONE group per item through PCCC-3/4 (the widened key changes identity, not behavior); fan-out is PCCC-5.

**Consumer audit (PCCC-3, by name):** every `graph_episodes` reader that assumes one-row-per-item or counts rows as items — the projector ledger read (above), `extraction-health.ts:362` (`count(*) … as team episode count`), `lib/query/retrieval-health.ts:143`, `lib/metrics/graph-efficiency.ts:24` ("a row is one ITEM"), and `lib/graph/extraction-alert.ts:99,125` (round-2 Medium 5 — recent-vs-baseline flow baselines; under fan-out rows inflate by P̄ mid-window → false flow-spike/drop alerts across the PCCC-5 boundary). Each is fixed to group-by or count-distinct-item as appropriate in this slice. Verified fan-out-safe already, recorded so the audit doesn't re-litigate them: `retireEpisodesForItems` (multi-row `.in()` read, `project.ts:446-471`) and reconcile's pending-cleanup (verifies per item within the group, not group-emptiness, `reconcile.ts:350-371`).

### 2.2 Projector — fan-out with change DETECTION as a set diff (net-new, leak-critical)

Under fan-out the projector resolves the item's **active include memberships** (`project_context_memberships` — the same set enforce/inspect read) → each project's **stored `graph_group_id`** (§2.4 — NOT computed from `projectGroupId` at read time), regardless of `items.access` (§2.0: tier-mixed by design), and reconciles the item's episodes into EACH project graph, each with its own per-`(item, group)` ledger row.

**The membership set is the WHOLE write rule — the home partition is NOT unconditional (Codex Blocker 1).** The earlier fold claimed today's `episodeGroupId(teamSlug, item.access)` home write "needs no change"; that contradicts the spec's move rule (`docs/specs/project-context-classification-v1.md:669-673`): restricting existing content MOVES it out of General — restricted content "can never sit in an Everyone-visible graph." So: for an unrestricted item the membership set includes General and the home write is unchanged in practice; for a RESTRICTED item (General membership closed) the set-diff's *removed* side purges the `_team`-pointer row like any other untag. The write mirrors memberships exactly, in every mode — and therefore the PERMISSIVE team-tier read must move off `visibleGroupIds` to the union of ALL the team's project partitions when restriction-purge activates (a team-tier permissive principal sees everything, so the union is coverage-equivalent; external permissive readers keep `_external` = external-shared's partition). **Sequencing consequence:** PCCC-5's fan-out is ADD-ONLY (new partitions only, no General removal); the restriction-purge side activates in PCCC-6 together with both read changes. That gap leaks nothing: under enforcing, attenuated principals still have the omit path until PCCC-6, and under permissive everyone sees everything by definition — while purging General any earlier would silently shrink permissive teams' graphs.

**Known accepted crash window (PCCC-3 code review, Fable Low 3):** on a double flip (A→B→A with outstanding debt on A), the group-move UPDATE durably re-points `pending_delete` to B *before* the A-purge runs; a process death between those two awaits leaves duplicates in A that nothing cleans. Requires double-flip + crash between adjacent awaits — accepted and documented rather than serialized, revisited if reconcile telemetry ever shows it firing.

The current detection is a single compare `tierChanged = existingRow.group_id !== groupId` (`project.ts:668`). Per-project it is a **SET DIFF** over the item's group rows: *added* (new membership → full push, paying extraction), *retained* (unchanged content → sha cache hit, free), *removed* (**untag** — isolation-critical). The removed side is **net-new machinery** (round-1 High 6): untagging an item from project P must set `pending_delete_group_id` on P's row and purge P's graph of that item — "restriction-moves-not-copies" is the leak-by-construction rule this enforces, and nothing existing detects membership-removal (reconcile's orphan repair covers item-gone only, `reconcile.ts:141`). This is scoped as real work, NOT "unchanged in shape."

- **Content-hash cache (per `(content_sha, group_id)`):** a re-tag/re-sync of unchanged content into a partition whose row already extracted is a zero-LLM hit; a FIRST tag into a partition pays. **Honest corrections (round-1 Medium 9; PCCC-5 code review Medium 4):** armed fan-out re-pushes are WHOLE-ITEM (the home path's per-chunk delta is not yet inherited — an edited document in k armed initiatives pays k × its full chunk count per edit; accepted at the measured rate, revisit if hot-document fan-out cost shows in the per-group ledger). And because untag purges and retires the row (isolation, above), a later re-tag into that same project RE-PAYS — the cache hit is real only for unchanged content re-syncing within a *persisting* membership, not "re-tag is always free."
- **Laziness + arming (resolves the readiness circularity, round-1 High 5):** extraction into a project with no reader is deferred to a **pending projection row** (net-new state — §2.5). It is armed **as a side effect of a read**: when a team-tier principal queries, their oracle-visible projects are scheduled for extraction, and the graph leg stays OMITTED for that principal until those projects' rows are reconcile-confirmed landed. So the first query arms-and-omits; later queries get the leg. No circularity — the query is the arming trigger, not a separate readiness handshake.

### 2.3 Read cutover — team-tier principals search their project graphs

`lib/query/retrieve` graph legs + `lib/graph/arcs` switch, FOR A TEAM-TIER ENFORCING PRINCIPAL, from `visibleGroupIds(tier)` to the **stored `graph_group_id` of each oracle-visible project** (§2.4) — resolving pointers, not minting keys; `graphGroupIdsForVisibleProjects` remains the mint-time scheme, and its role note in `lib/graph/group.ts` is amended in PCCC-3 to say so ("single authority" for MINTING, with `projects.graph_group_id` authoritative for reads). Only projects whose graph is **read-ready** participate; an un-ready project keeps the leg omitted for that principal. External-tier principals and permissive teams are unchanged (external stays omitted; permissive keeps the tier path — which reads the SAME `_team`/`_external` groups the built-ins' pointers name, so the pointer adoption cannot go dark for permissive teams).

**Read-ready is a MONOTONE LATCH over an arm-time OBLIGATION SNAPSHOT (round-2 High 4, corrected by Codex Blocker 2).** "All rows currently landed" is non-monotonic — landing is per-item and asynchronous with a grace of at least one full projection cycle (`reconcile.ts:29-45`), so a busy initiative would starve forever and a landed project would flap on every new tag. But a `projected_at ≤ watermark` timestamp latch is vacuously true for exactly the rows arming exists to wait for: a cold project's rows are all deferred (excluded), so it would latch ready over an EMPTY graph, and arming's own conversion bumps `projected_at` past the watermark. So the watermark is an **item-id snapshot, not a timestamp**: arming records the project's member item-ids as of arm time; the project latches read-ready when EVERY snapshotted item has a reconcile-confirmed landed row in the group (202 ≠ extracted). Deferred rows COUNT as unmet obligations — they are precisely the work arming schedules; `pending_delete` rows are excluded from the snapshot (they are leaving). Once latched, ALWAYS latched — items tagged after the snapshot lag exactly the way today's tier graph lags, and never un-ready the leg. The latch persists (state, not cache).

**Suppression scope, as built (PCCC-6a second-pass review High 4):** the read-time purge-suppression below applies to INITIATIVE partitions only. A self-purge in a BUILT-IN is routine (every redaction, deletion, and restriction move-out flags a General row for at least the hour-scale cleanup grace), so suppressing built-ins blanked the enforced leg's primary partition near-constantly — the §7.5 falsifier pre-fired. The ONE built-in exception is General's **restriction debt** (Codex code-review Blocker 1, superseding the earlier "accepted residual" ruling, which contradicted spec rule 2's absolute language — restricted content can never be servable through an Everyone-visible graph): while any restriction move is short of purge-confirmed (live home row, or move-out written but the Graphiti deletion unconfirmed), ENFORCED reads fail closed on General via `generalHoldsRestrictedContent` — a read-time, substrate-discriminated probe (the `resolveFanoutTargets` inGeneral complement in SQL, co-located with it), so routine redaction/deletion hygiene never trips it and the built-in exemption otherwise stands. The permissive union is exempt (no enforcement exists there to protect; blanking would go dark for the default mode). `restrictionMovesPending` remains the OBSERVABILITY of the window, not its mitigation. Also named: EXTERNAL-access items are exempt from the restriction move (their home is external-shared, not General — rule 2 speaks to General; the external-shared analogue is 6b/follow-up territory), and armed-but-unpushed ledger rows (empty chunk ledger) are the PROJECTOR's to converge — reconcile's never-landed judge skips them, or a reader-quiet team's restriction copies would be deleted-and-re-deferred every cycle, holding the rule-2 window open forever (second-pass Blocker 2). Restriction also writes the ARMING ROW itself (second-pass Blocker 1): without it no permissive read ever latches the partition and the moved content would leave General yet be servable from nowhere.

**But the latch alone would hold a leak open (Codex Blocker 3): a partition that owes a purge is SUPPRESSED until the purge confirms.** Untag is a NARROWING transition, and reconcile deliberately leaves cleanup pending when Graphiti is unreachable or the scan saturates (`reconcile.ts:332-337`) — so "eventually consistent" is unbounded under outage, and a P-only principal would keep reading an untagged item's facts from P's graph the whole time. Graphiti search has no per-fact filter (the §5.8b premise), so the only fail-closed unit is the partition: a group with outstanding `pending_delete` rows is OMITTED from enforced reads until its purge is reconcile-confirmed. This is a separate read-time conjunct, NOT an un-latching — readiness stays monotone; suppression is temporary and bounded by purge latency (chronic suppression is a falsifier, §7.5).

**The graph stage is K-CAPPED per the spec's expansion budget (Codex Medium 8 — the first drafts dropped it, `docs/specs/project-context-classification-v1.md:592-606`):** the graph legs cover the top-K ready, unsuppressed, oracle-visible partitions (K = 8 default, configuration not constant), router = recency prior only until Phase D's profile embeddings exist, **General always included**, with the answer footer disclosing scope ("graph expansion covered 8 of your 37 projects" — the spec's deliberate own-scope exception to §5.7). FTS/dense stay complete over the full visible set, so correctness never depends on the router; beyond-cap partitions lose only graph-flavored recall. Latency ceiling: p95 end-to-end ≤ 2× today's single-scope query, measured at K ∈ {1, 8, 16} BEFORE cutover (§7.6).

### 2.4 Migration — the spec's STORED-POINTER design; nothing renamed, nothing re-extracted

The first draft's "dual-write doubles cost for newly-projected items only" was false (round-1 Blocker 2): `runGraphProjection` rescans the WHOLE corpus from an undefined cursor every pass (`run.ts:125`), and every item is in General, so a naive fan-out re-extracts the entire corpus into General on the first pass — an immediate unthrottled spike that also trips the Graphiti queue-wedge (`reconcile.ts:35`). The round-1 fold's "General REMAP/rename" was ALSO wrong (round-2 Blocker): the governing spec had already ruled this question, and every branch of the remap idea had a silently-empty-partition or full-re-extraction failure (a rename empties the `_team` group that permissive teams — the DEFAULT mode, `lib/access/enforce.ts:11` — still read; a `graph_episodes.group_id` remap away from where the facts live makes reconcile's landed-check read every row as never-landed and re-extract the corpus at requeue speed). **The design is the spec's (`docs/specs/project-context-classification-v1.md:946-950`): Graphiti has no rename operation, so nothing is renamed — `projects` gains a `graph_group_id` column; General records the legacy `<teamSlug>_team` id and external-shared records `<teamSlug>_external`; the existing graphs become those projects' partitions BY POINTER, not by rewrite. New projects mint `projectGroupId(teamId, projectId)` ids. Exactly two grandfathered exceptions per team, stored not inferred. Nothing is re-extracted — migration cost ≈ 0, no spike, no spike-shaped fallback.** Corrected sequence:

1. **PCCC-3 (Deploy A)** — wide unique index + 4-column conflict targets + per-group ledger + loud upsert errors + consumer audit (§2.1). Behavior-preserving.
2. **PCCC-4 (Deploy B)** — drop the narrow unique (§2.1 step 2); add `projects.graph_group_id` (additive migration + `schema.sql` mirror) with the grandfathered pointers backfilled and **ONE pointer writer (Codex High 5):** a single helper (e.g. `ensureProjectGraphPointer`) called by EVERY project-creation path — the built-ins bootstrap (`lib/access/bootstrap.ts`), initiative creation (`app/actions/projects.ts`), ingest-created source projects (`lib/ingest/index.ts`), and meeting projects (`lib/meetings/extract-todos.ts`) — because the column is net-new and today NO path writes it; a team created after the migration with unpointered built-ins would write to legacy groups while reads resolve nothing. The rule holds for ALL teams, old and new: built-ins record the legacy tier ids for as long as the home write path is `episodeGroupId`; initiatives mint `projectGroupId`. **Null-freedom doctrine (amended as built — a DB `NOT NULL` is NOT implementable here):** every creation path is insert-then-point (the two upsert paths cannot carry a pointer atomically — the adapter's conflict-update would clobber existing rows' ids), so the column stays nullable and the invariant is enforced as: the required-call-sites guard (build-failing), the partial unique (injectivity), the backfill migration REPLAYING ON EVERY DEPLOY (`pg:schema` runs all migrations — any ordinary project that slipped through null is minted at the next deploy; built-ins converge via the scheduler-tick bootstrap), and PCCC-6 readers treating null as not-cutover, fail closed. Charset/uniqueness guard-tested (it is a security-boundary value). Amend `lib/graph/group.ts`'s authority note (§2.3). Still one group per item; ~0 LLM.
3. **PCCC-5 — initiative fan-out, ADD-ONLY (§2.2), deferral-gated, with a REAL push budget.** Fan-out into initiative projects is where genuine new extraction happens; the restriction-purge (General-removal) side stays OFF until PCCC-6 (§2.2). It ships behind a projector-side **push budget** — a NEW cap (the cited `GRAPH_REQUEUE_MAX_PER_PASS` is reconcile's re-queue budget, `reconcile.ts:81`, NOT a projector push cap) — and behind arming (§2.2), so cold initiatives never extract. The cost gate (§3) sits BEFORE this slice and is real: nothing schedules initiative fan-out until the quiet-window baseline + the priced estimate are in hand.
4. **PCCC-6 — read cutover + the writes that must co-land with it:** the enforcing team-tier graph legs move to ready, unsuppressed, K-capped project partitions (§2.3); the permissive team-tier read moves to the all-partitions union and restriction-purge activates (§2.2); and **arc corrections partition (Codex High 6)** — today corrections are team-global (no project/group key on the table, `schema.sql:2466-2478`), feed EVERY team-tier synthesis (`lib/graph/arcs.ts:717-736`), and write their correction episodes into the legacy team group (`arcs.ts:1312-1327`, `episodeGroupId(slug,'team')`), so a correction carrying restricted prose would launder into an Everyone-visible arc — the spec forbids cross-partition synthesis outright (`spec:688-690`). PCCC-6 scopes corrections by group (schema + write-back targeted at the corrected arc's OWN group); until that lands, corrections are EXCLUDED from any synthesis serving an enforced principal (fail closed on laundering). **As built (PCCC6B-1) — with an honesty correction first: the interim exclusion this step promised was NEVER implemented.** Until 6b, an enforcing team's members read the shared tier `arc_cache` row whose synthesis consumed ALL team corrections (`arcs.ts:717-736` gates only on tier, and `synthesizeArcs` receives no principal); the only shipped mitigation was the visibility-scoped WRITE gate (`recompute/route.ts:82-89`), which bounds who can create a correction, not who consumes one. 6b closes the hole structurally instead of patching the interim: **(a) corrections are scope-keyed** — `arc_corrections.group_key` records the synthesis scope (the same sorted group-set key `arc_cache` uses) the corrected arc was served from, synthesis loads corrections by EXACT scope match, and the legacy tier path additionally accepts `''` (pre-6b rows are tier-scope by construction — the recompute route has always refused external principals). Scope-equality is deliberately conservative: a correction never feeds a different scope, not even a superset, so no cross-visibility path exists to reason about. Correction IDENTITY is per-scope too (`unique (team_id, group_key, arc_id)` — Fable 6b High 2: `arc_id` is sha(title) and near-identical scopes mint identical titles, so the old team-global unique let one member's correction silently MOVE another member's row across scopes, reverting the victim's arcs). A partition scope whose groups are ALL external-shaped still loads its own corrections — the scoped row is served only to team-tier members, and refusing would silently revert a correction made during a restriction-debt window (Fable 6b Medium 4). **(b) The graph write-back follows the scope:** tier scope keeps today's `<slug>_team` target (safe — the team group is unreadable to external-tier readers); a SINGLE-group partition scope writes to that group UNLESS the group is external-shaped (Fable 6b High 1: during a restriction-debt window an enforced member's whole scope is `[<slug>_external]`, and a team correction written there would be searchable by external principals forever); a MULTI-group partition scope writes NOTHING to the graph — the prose derives from the union, so any single target narrower than its derivation scope is the laundering this step exists to prevent (the Postgres row still feeds same-scope synthesis via the prompt). **(c) The enforced arcs read cutover:** an enforcing team-tier member's arcs move off the tier cache entirely — synthesis runs over their ready-and-unsuppressed partition scope (`selectEnforcedGraphPartitions`, arm-on-read, uncapped: the fact pool already bounds synthesis input), cache-keyed by that scope, so the tier row is only ever served to permissive readers and external-tier members (whose paths are unchanged, per §2.3). Per-scope cache rows mean per-distinct-oracle synthesis cost — bounded by active arc READERS (no cron path exists), the 4h TTL, and the fact pool. The PCCB-5 evidence filter stays as defense-in-depth. Named boundary: `lib/social/discover-arcs.ts` keeps the tier path — a pre-existing principal-less surface, out of 6b's scope.
5. **PCCC-7 — cleanup:** invalidate tier-keyed `arc_cache` rows (`group_key` = sorted group-set key, `schema.sql:2442-2456`) so stale synthesized arcs don't outlive their read paths. Retiring the `_external` group stays OUT of Phase C (§2.0) — it is external-shared's live partition.

**Concurrency (round-1 Medium 11):** the pointer backfill and any fan-out scheduling run THROUGH the in-process `runGraphProjection` single-flight (`run.ts:73`) or take a DB advisory lock — never as a separate script racing the hourly runner (duplicate episodes, since `addEpisodes` never overwrites by name).

### 2.5 Net-new state this design introduces (was implicit)

- **`projects.graph_group_id`** (spec-ruled, §2.4) — the stored partition pointer; `projectGroupId` is its mint default, the two built-ins grandfather the legacy tier ids; ONE writer helper across every creation path. **Team-rename doctrine (PCCC-4 code review, named not discovered later):** the pointer is frozen at first write, but `episodeGroupId` re-keys from the CURRENT slug at every projection — so after a rename, new episodes land in `<newslug>_*` groups while the pointer names `<oldslug>_*`; every episode projected between a rename and the PCCC-6 cutover is invisible to the pointer. And the doctrine is asymmetric by construction: a team renamed BEFORE the backfill points at its new slug's groups, one renamed AFTER keeps the old. Resolution direction: PCCC-5 makes the projector resolve the home group FROM the pointer (dissolving the divergence — one authority); until then, rename + enforcing is a named-incoherent combination. Slug REUSE after a rename wedges the new team's bootstrap LOUDLY in both orders (Codex code review High 1 closed the silent one): post-backfill reuse collides on the pointer unique, and PRE-backfill reuse — where the old team's pointer moved to its new slug, leaving its historical episodes unclaimed under the old slug's group — is refused by the writer's FOREIGN-HISTORY check (any `graph_episodes` row for that group under another team id) and skipped by the backfill's matching `not exists` guard; both paths name the manual repair.
