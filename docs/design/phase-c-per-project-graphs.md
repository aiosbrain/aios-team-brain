# Phase C — per-project graph projection & migration (design)

**Status:** design, pre-code, **revised after TWO Fable plan-review rounds** (round 1: 2 Blockers + 5 Highs + 2 Mediums, folded; round 2: BLOCKED — 1 Blocker + 3 Highs + 3 Mediums + 3 Lows, folded — the Blocker being that the first fold's General-remap contradicted the design the governing spec had already ruled). Governs the Phase C graph slices (spec `docs/specs/project-context-classification-v1.md` §6 / §17-C). `AIOS-Work: PCCC-2`.
**Gate:** touches schema + LLM extraction cost + multiple surfaces (CLAUDE.md task gate) — reviewed as a plan before any code slice starts. A Codex adversarial plan review runs on this revision before the PR pushes; PCCC-3 does not open until the reviewed doc merges.
**Build-with:** fable / high — the code slices this doc governs change the graph's partition key, prod schema, and real LLM spend; each gets its own PR + two-model adversarial review.
**Increment:** one PR, docs only. Every code change is deferred to the sibling slices PCCC-3..7 (§5), each its own ticket + PR + review.

## 1. Problem

The Graphiti graph is partitioned by **tier**: an item's episodes live in `<teamSlug>_team` or `<teamSlug>_external` (`lib/graph/project.projectItemsToGraph` → `episodeGroupId(teamSlug, item.access)`), and a reader searches `visibleGroupIds(tier)`. That write-time `item.access` split is the ONLY graph isolation (no RLS).

Phase B enforced the **item** reads at project grain but could not enforce the **graph** legs — the mirrors are tier-partitioned, not project-partitioned. PCCB-2 handled it by **OMITTING the graph legs for any attenuated/partitioned principal under enforcing** (§5.8b): safe but lossy. Phase C re-enables them by partitioning the graph per project (PCCC-1 landed the key scheme `projectGroupId`/`graphGroupIdsForVisibleProjects`).

## 2. Decision

### 2.0 Scope correction from review — TWO invariants the first draft dropped

- **Tier isolation is NOT subsumed by project partitioning (round-1 High 3).** `project_context_memberships` is orthogonal to `items.access`: an initiative project can hold BOTH team- and external-access items, and Graphiti search has no per-fact filter (the whole §5.8b motivation). So a project graph is tier-MIXED. An external-tier principal visible to project P via the External built-in would otherwise read team-tier facts from P's graph. **Decision: Phase C re-enables the per-project graph legs for TEAM-TIER principals only. External-tier principals KEEP the omit path** (as today) — they are a minority (client/consultant collaborators), team-tier principals `canSeeAccess` every access level so a tier-mixed project graph is safe *for them*, and this avoids doubling every partition into `(project, tier)`. Retiring the `_external` tier group is therefore explicitly OUT of Phase C — that group stays live as the external-shared built-in project's partition (§2.4). `projectGroupId` stays tier-free; the tier axis lives in the READ (external → omit), not the key. **And the fan-out set follows from this (round-2 High 3 — the first fold contradicted itself):** ALL of an item's active include memberships fan out, regardless of `items.access` — an external-access item tagged into initiative P lands in P's graph. Project graphs are tier-mixed *by design*; the untag matrix and P̄ count external-access items like any other. Team-tier readers do NOT lose the external-access content they get today from `visibleGroupIds(team) = [_team, _external]`: the external-shared built-in project's partition IS `<teamSlug>_external` by stored pointer (§2.4), so when that project is in their oracle-visible set, its group is in their read set.
- **The content-hash cache must key on `(content_sha, group_id)`, and it does not today (round-1 Blocker 1).** The projector's ledger read is `.eq("source_id", item.id).maybeSingle()` (`project.ts:616-622`) — one row per item — and this adapter's `maybeSingle` returns `rows[0]` SILENTLY on multiple rows (`lib/db/pg/query-builder.ts:336`). So the moment fan-out writes a second row, the projector reads an arbitrary group's ledger; a sha-match against the wrong group SKIPS extraction into a group that never got the content → a **silently-empty project graph**. The per-`(item, group)` ledger read is therefore not an optimization — it is the correctness precondition, and it lands in the SAME slice as the schema.

### 2.1 Schema + projector conflict-target — ONE coupled slice (was "additive"; it is not)

The unique key widens `(team_id, source_table, source_id)` → `+ group_id`. This is **NOT additive** — both projector upserts conflict on the OLD 3-column key (`project.ts:661,893`, emitted verbatim as `ON CONFLICT (…)`), and Postgres requires a unique index exactly matching the conflict target. A single coupled deploy is ALSO wrong (round-2 High 2): `pg:schema` runs as Railway's preDeploy hook (`scripts/pg-load-schema.mjs:7`) while the OLD release still serves, so dropping the narrow unique in the same migration breaks the old code's 3-column `ON CONFLICT` ("no unique or exclusion constraint matching") for the whole deploy window — and **both ledger upserts discard their returned error today** (`project.ts:650, 878-894`), so the failure would be silent: episodes pushed to Graphiti, ledger never written, re-pushed next pass → duplicate episodes; the redaction branch would delete episodes and silently fail to record `pending_delete`. **The sequence is therefore TWO deploys, no broken window in either direction:**

1. **Deploy A (PCCC-3):** migration adds the wide unique as an identically-named `create unique index if not exists … (team_id, source_table, source_id, group_id)` in BOTH the migration and `schema.sql` (round-2 Medium 7 — an inline `unique (…)` mirror in `create table` would auto-name differently and give a from-zero DB two identical arbiter indexes; the narrow unique stays inline at `schema.sql:2382` until Deploy B). Same PR, same deploy: both projector `onConflict` → the 4-column key; the ledger read → `.eq("source_id", item.id).eq("group_id", groupId).maybeSingle()` (per-group); the change-detection (§2.2); **both upserts destructure and fail LOUD on `{ error }`** (the silent discard above is what would have made every window failure invisible); and an explicit-UPDATE path for the group-move case (a tier flip changes `group_id` on the same logical row — under the 4-column target that's an INSERT of a second row, which the still-standing narrow unique rejects; while it stands, group-move is an UPDATE by the old key). Old code during A's window conflicts on the 3-column target, which still matches the narrow unique — safe.
2. **Deploy B (opens PCCC-4):** migration does `alter table graph_episodes drop constraint if exists <narrow unique>` (replay-safe — migrations re-run on every deploy, `postgres/migrations/README.md`) and removes it from `schema.sql`'s `create table`; the explicit-UPDATE group-move path relaxes to the plain 4-column upsert. Old code during B's window is Deploy A's code (4-column target vs the wide index) — safe.

The projector still computes ONE group per item through PCCC-3/4 (the widened key changes identity, not behavior); fan-out is PCCC-5.

**Consumer audit (PCCC-3, by name):** every `graph_episodes` reader that assumes one-row-per-item or counts rows as items — the projector ledger read (above), `extraction-health.ts:362` (`count(*) … as team episode count`), `lib/query/retrieval-health.ts:143`, `lib/metrics/graph-efficiency.ts:24` ("a row is one ITEM"), and `lib/graph/extraction-alert.ts:99,125` (round-2 Medium 5 — recent-vs-baseline flow baselines; under fan-out rows inflate by P̄ mid-window → false flow-spike/drop alerts across the PCCC-5 boundary). Each is fixed to group-by or count-distinct-item as appropriate in this slice. Verified fan-out-safe already, recorded so the audit doesn't re-litigate them: `retireEpisodesForItems` (multi-row `.in()` read, `project.ts:446-471`) and reconcile's pending-cleanup (verifies per item within the group, not group-emptiness, `reconcile.ts:350-371`).

### 2.2 Projector — fan-out with change DETECTION as a set diff (net-new, leak-critical)

Under fan-out the projector resolves the item's **active include memberships** (`project_context_memberships` — the same set enforce/inspect read) → each project's **stored `graph_group_id`** (§2.4 — NOT computed from `projectGroupId` at read time), regardless of `items.access` (§2.0: tier-mixed by design), and reconciles the item's episodes into EACH project graph, each with its own per-`(item, group)` ledger row. The item's grandfathered home partition needs no write change at all: today's `episodeGroupId(teamSlug, item.access)` write IS "write the item into its home built-in's partition" once General's pointer records `<teamSlug>_team` and external-shared's records `<teamSlug>_external`.

The current detection is a single compare `tierChanged = existingRow.group_id !== groupId` (`project.ts:668`). Per-project it is a **SET DIFF** over the item's group rows: *added* (new membership → full push, paying extraction), *retained* (unchanged content → sha cache hit, free), *removed* (**untag** — isolation-critical). The removed side is **net-new machinery** (round-1 High 6): untagging an item from project P must set `pending_delete_group_id` on P's row and purge P's graph of that item — "restriction-moves-not-copies" is the leak-by-construction rule this enforces, and nothing existing detects membership-removal (reconcile's orphan repair covers item-gone only, `reconcile.ts:141`). This is scoped as real work, NOT "unchanged in shape."

- **Content-hash cache (per `(content_sha, group_id)`):** a re-tag/re-sync of unchanged content into a partition whose row already extracted is a zero-LLM hit; a FIRST tag into a partition pays. **Honest correction (round-1 Medium 9):** because untag purges and retires the row (isolation, above), a later re-tag into that same project RE-PAYS — the cache hit is real only for unchanged content re-syncing within a *persisting* membership, not "re-tag is always free."
- **Laziness + arming (resolves the readiness circularity, round-1 High 5):** extraction into a project with no reader is deferred to a **pending projection row** (net-new state — §2.5). It is armed **as a side effect of a read**: when a team-tier principal queries, their oracle-visible projects are scheduled for extraction, and the graph leg stays OMITTED for that principal until those projects' rows are reconcile-confirmed landed. So the first query arms-and-omits; later queries get the leg. No circularity — the query is the arming trigger, not a separate readiness handshake.

### 2.3 Read cutover — team-tier principals search their project graphs

`lib/query/retrieve` graph legs + `lib/graph/arcs` switch, FOR A TEAM-TIER ENFORCING PRINCIPAL, from `visibleGroupIds(tier)` to the **stored `graph_group_id` of each oracle-visible project** (§2.4) — resolving pointers, not minting keys; `graphGroupIdsForVisibleProjects` remains the mint-time scheme, and its role note in `lib/graph/group.ts` is amended in PCCC-3 to say so ("single authority" for MINTING, with `projects.graph_group_id` authoritative for reads). Only projects whose graph is **read-ready** participate; an un-ready project keeps the leg omitted for that principal. External-tier principals and permissive teams are unchanged (external stays omitted; permissive keeps the tier path — which reads the SAME `_team`/`_external` groups the built-ins' pointers name, so the pointer adoption cannot go dark for permissive teams).

**Read-ready is a MONOTONE LATCH, not a live predicate (round-2 High 4).** "All rows currently landed" is non-monotonic — landing is per-item and asynchronous with a grace of at least one full projection cycle (`reconcile.ts:29-45`), so a busy initiative would sit perpetually ≥1-un-landed (starved forever) and a landed project would flip back to omitted for everyone each time one item is tagged in (the leg flaps). Instead: arming (§2.2) records a **watermark**; the project becomes read-ready when every ledger row for its membership set with `projected_at ≤ watermark` is reconcile-confirmed landed (202 ≠ extracted), excluding `pending_delete` and deferred rows, which never count toward readiness. Once ready, ALWAYS ready — items tagged after the watermark lag exactly the way today's tier graph lags (eventual consistency), and never un-ready the leg. Computing the latch is a bounded aggregate over the project's rows; the latched bit persists (it is state, not a cache — recomputing it must not un-latch it).

### 2.4 Migration — the spec's STORED-POINTER design; nothing renamed, nothing re-extracted

The first draft's "dual-write doubles cost for newly-projected items only" was false (round-1 Blocker 2): `runGraphProjection` rescans the WHOLE corpus from an undefined cursor every pass (`run.ts:125`), and every item is in General, so a naive fan-out re-extracts the entire corpus into General on the first pass — an immediate unthrottled spike that also trips the Graphiti queue-wedge (`reconcile.ts:35`). The round-1 fold's "General REMAP/rename" was ALSO wrong (round-2 Blocker): the governing spec had already ruled this question, and every branch of the remap idea had a silently-empty-partition or full-re-extraction failure (a rename empties the `_team` group that permissive teams — the DEFAULT mode, `lib/access/enforce.ts:11` — still read; a `graph_episodes.group_id` remap away from where the facts live makes reconcile's landed-check read every row as never-landed and re-extract the corpus at requeue speed). **The design is the spec's (`docs/specs/project-context-classification-v1.md:946-950`): Graphiti has no rename operation, so nothing is renamed — `projects` gains a `graph_group_id` column; General records the legacy `<teamSlug>_team` id and external-shared records `<teamSlug>_external`; the existing graphs become those projects' partitions BY POINTER, not by rewrite. New projects mint `projectGroupId(teamId, projectId)` ids. Exactly two grandfathered exceptions per team, stored not inferred. Nothing is re-extracted — migration cost ≈ 0, no spike, no spike-shaped fallback.** Corrected sequence:

1. **PCCC-3 (Deploy A)** — wide unique index + 4-column conflict targets + per-group ledger + loud upsert errors + consumer audit (§2.1). Behavior-preserving.
2. **PCCC-4 (Deploy B)** — drop the narrow unique (§2.1 step 2); add `projects.graph_group_id` (additive migration + `schema.sql` mirror) with the two grandfathered pointers backfilled per team and `projectGroupId` as the mint default for new projects; amend `lib/graph/group.ts`'s authority note (§2.3). Still one group per item; ~0 LLM.
3. **PCCC-5 — initiative fan-out, deferral-gated, with a REAL push budget.** Fan-out into initiative projects is where genuine new extraction happens. It ships behind a projector-side **push budget** — a NEW cap (the cited `GRAPH_REQUEUE_MAX_PER_PASS` is reconcile's re-queue budget, `reconcile.ts:81`, NOT a projector push cap) — and behind arming (§2.2), so cold initiatives never extract. The cost gate (§3) sits BEFORE this slice and is real: nothing schedules initiative fan-out until the quiet-window baseline + the priced estimate are in hand.
4. **PCCC-6 — read cutover** (§2.3), team-tier only, gated on the per-project read-ready latch.
5. **PCCC-7 — cleanup:** invalidate tier-keyed `arc_cache` rows (`group_key` = sorted tier-group set, `schema.sql:2399`) so stale synthesized arcs don't outlive their read paths. Retiring the `_external` group stays OUT of Phase C (§2.0) — it is external-shared's live partition.

**Concurrency (round-1 Medium 11):** the pointer backfill and any fan-out scheduling run THROUGH the in-process `runGraphProjection` single-flight (`run.ts:73`) or take a DB advisory lock — never as a separate script racing the hourly runner (duplicate episodes, since `addEpisodes` never overwrites by name).

### 2.5 Net-new state this design introduces (was implicit)

- **`projects.graph_group_id`** (spec-ruled, §2.4) — the stored partition pointer; `projectGroupId` is its mint default, the two built-ins grandfather the legacy tier ids.
- A **per-`(item, group)` ledger** (the widened key) — the correctness substrate.
- **Untag detection + purge** (§2.2 removed-side) — leak-critical.
- A **deferred/pending projection** state distinct from reconcile's `content_sha256 = ''` sentinel, which already means three things (re-queued / redacted / retired). A deferred row must NOT be deleted by reconcile's landed-check (`reconcile.ts:312` deletes never-landed rows past the grace) — it needs its own flag + a reconcile exemption. Under-specced in the first draft; scoped here.
- The **read-ready latch + arming watermark** (§2.3) — persisted monotone state, not a cache.
- A projector **push budget** (§2.4 step 3) — new, distinct from the reconcile re-queue budget.

## 3. Cost model — re-measured, backfill priced at the CURRENT rate

The first draft juxtaposed two per-episode rates 10× apart (round-1 High 7): the §6 measured $0.151/episode vs the CHUNKCAP $0.0147/episode anchor — different model/routing eras. **Neither is trusted:** re-measure per-`(episode, partition)` cost from `llm_usage source=graph` over a QUIET window (no backfill) before PCCC-5 schedules. Then:

- **Steady state — ONE P̄ definition (round-2 Medium 6):** P̄ = mean partitions per item, home built-in INCLUDED (the spec's definition, spec line 643) — a classified item costs P̄× total, (P̄ − 1)× marginal beyond its home. Aggregate: cost ≈ baseline × (1 + share_multi × (P̄multi − 1)). There is NO dual-write phase anywhere in this design (the home partition is a pointer, §2.4) — the term is retired; the marginal cost is initiative fan-out only.
- **One-time backfill = initiative fan-out only** (home partitions are pointers, §2.4). Priced from the REAL count of (items classified into an initiative) × current per-episode rate, throttled through the push budget, lazy for cold initiatives — estimated before scheduling; if unacceptable, lazy-only (fan out on next re-sync / on arm, no eager backfill).
- **Per-project cost visibility (round-1 High 4 — the metering claim was false):** the graph proxy CANNOT attribute per-call group (Graphiti's completion calls carry no episode context — `graph-proxy.ts:92`; per-call attribution needs an upstream graphiti_core change). So per-project spend is **APPROXIMATED** from the per-`(item, group)` episode count in `graph_episodes` (episodes-per-project as a cost proxy), not exact `llm_usage` attribution. The per-team ceiling stays the only HARD cap; a per-project soft cap is a later item contingent on the upstream change. The governing spec still asserts the per-call metering (spec §6, "the proxy already tags calls") — **that spec bullet is amended in this same PR** (round-2 Low 8) so the two documents don't disagree permanently.

- **External-tier per-project graph reads** — external principals keep the omit path (§2.0). Unticketed until an external-tier principal needs graph-grounded answers (a product signal, not a Phase C dependency); ticket then opens against a per-`(project, tier)` or per-fact-filter design.
- **The Postgres `graph_entities`/`graph_relationships` mirrors** (`/api/v1/query` structured legs) — a separate `group_id` leg. Unticketed until the PCCC-6 read cutover lands (its shape depends on the pointer scheme proving out).
- **Per-project arcs** (the structural fix for the PCCB-5 synthesized-prose residual) — unticketed until PCCC-6 lands; it consumes the per-project graphs this doc builds.

## 7. Falsifiers

1. Quiet-window per-episode cost materially above §6 → P̄ multiplier unaffordable → keep the graph legs omitted for attenuated principals (accept the UX loss), General-only graph.
2. The grandfather equivalence fails — General's membership set materially diverges from the `_team` ledger set (measured BEFORE PCCC-4 by diffing General's `project_context_memberships` against `graph_episodes` rows in `<teamSlug>_team`) → the pointer mislabels the home partition → General needs selective re-projection of the diff (priced first), not pure pointer adoption.
3. A `graph_episodes` consumer depends on one-row-per-item in a way the widening can't preserve → §2.1 reworks before anything downstream.
4. Untag-purge (§2.2) proves unreliable (a removed membership leaves facts in P's graph) → restriction is not leak-safe → the whole re-enable is blocked; legs stay omitted.
