# AIO-1170 — Slack contribution and timeline reliability

Status: Stage 1 draft for Fable review; no implementation or live incident certification.
Basis: `origin/staging` at `d1f0c088`, guidance checkpoint `df333a8a`, inspected 2026-09-09. Target PR: `staging`; merge, deployment and production repair are separate authorization boundaries. The original Linear scope remains the outcome contract. This replaces hypotheses derived against a different checkout with the findings below.

## What / why and outcomes

An eligible authored Slack message from a selected, verified-public channel must eventually produce evidence for the correctly linked person on its original contribution day. The evidence grain is `(thread, member, UTC day)`. Later replies cannot move previous days. Identity is attribution only: it never grants content access. Slack remains the existing in-app connector and `ingestItem` remains the item writer. No Python source, private-channel/DM ingestion, Events API prerequisite, new ACL model, or replacement of contributor correction locks is introduced.

This design chooses durable bounded polling and fair historical reconciliation. A full retained-history scan discovers old roots; a rotating revisit of ALL known roots discovers new replies even if history never resurfaces them. A larger first-page cap is not a fix. This proves eventual discovery, not arbitrary-corpus discovery in two ordinary scheduler ticks. The original two-interval latency is a proposed live target to measure, and must be reported as unmet if the measured cycle exceeds it. If a strict two-tick old-thread SLA becomes mandatory, the scope must add verified Slack Events delivery plus reconciliation; do not claim the polling design meets it by redefining an interval.

## Message ledger and canonical identity

Add a single source-owned metadata ledger, `slack_messages`, and durable polling state. Proposed schema (names may change in reviewed implementation, invariants may not):

* `slack_messages`: `team_id`, `workspace_id`, `channel_id`, `message_ts` (exact Slack string), `root_ts`, `item_id`, `author_external_id`, `occurred_at timestamptz`, `is_root`, `eligible`, `exclusion_reason`, `deleted_at`, `last_seen_generation`, `source_hash`, `observed_at`. Unique `(team_id,workspace_id,channel_id,message_ts)`; item FK with cascade and team-consistency checks; index `(team_id,occurred_at,item_id,message_ts)` and scoped author index. Do not store duplicate message bodies, email, or access grants here. Exact microsecond timestamp parsing determines the instant; never generate identity from a floating-point value.
* `slack_sync_channels`: unique `(team_id,workspace_id,channel_id)`; integration binding/config revision, verified-public status and checked time, history anchor/cursor/completed lower bound, scan generation, lease owner/expiry/fencing generation, retry-not-before, categorized error, last provider read, last persisted contribution and last full cycle completion. Multiple connector configurations selecting the same channel coalesce into this key; their access/config bindings are validated before every claim.
* `slack_sync_threads`: same scope plus `root_ts`; canonical `item_id`, due time, attempts, lease/fence, hydration generation, complete-read time, pending/error state. Index due work. Persist thread-page progress/staged snapshot in source-owned staging records (bounded by configured byte budget), with expiry and generation; do not publish incomplete pages. Stage only what is required to finish a canonical body, subject to the same purge rules as that body. Interrupted/expired snapshots restart safely.

A Slack account is provider `slack`, qualified external identity `WORKSPACE_ID:USER_ID`; both components are validated, canonicalized once, and exposed separately in public DTOs. AIOS `team_id` is always an additional namespace. Slack Connect authors use the user identifier as observed in the connected workspace; do not guess equivalence to a home-workspace login. Multiple qualified accounts may map to the same member.

New canonical item paths include workspace and channel: `slack/<workspace>/<channel>/<root-ts>.md`. Existing paths must migrate in place, retaining item IDs, versions, project/context relationships and locks. Record verified workspace provenance in frontmatter. Backfill workspace ONLY from matching verified integration/auth metadata and channel ownership; an env-token assumption or one current integration is insufficient evidence for ambiguous historical content. Collision/unknown provenance is quarantined for admin correction, never overwritten or duplicated. All cleanup/purge path helpers must accept workspace; old unqualified paths use their recorded migration mapping. An integration switch to another workspace creates new scoped state, never reuses the previous cursor/item identity.

Compatibility: `member_identities` stays the sole writer. Retain legacy plain-ID rows until migrated by an audited, idempotent repair through that writer. A plain ID resolves only when the caller supplies a verified workspace that has a unique compatible mapping, or when the complete team account set proves one unambiguous account. Conflicts and multiple workspaces yield an explicit ambiguity, not first-row wins. New OAuth, pasted-token, auto-sync, admin-link, attribution, credit, list and resolve consumers must use the same parser/resolver. `/api/v1/identities/resolve` retains its existing query fields and DTO: qualified selection uses the existing `external_id` parameter, and accounts remain in the existing `identities` array. `slack_id` remains a RAW user ID for the explicitly selected account or one unambiguous account, and is null for ambiguous email/handle selection; never return the qualified string as a Slack wire ID. No new endpoint, query parameter or response field is needed. Verify current CLI consumers tolerate the existing nullable `slack_id`; document qualified IDs using the existing generic external-ID contract. If consumer inspection proves an unavoidable breaking change, stop that change for coordinator adjudication rather than silently expanding cross-repo scope. Do not expand the member-secret store to multiple active Slack tokens; this feature supports multiple identity links independently of that existing credential limit.

## Polling, publication and failure semantics

1. Verify `auth.test` workspace, installed token capability and selected public channel with read-only calls. Record token category/scopes when authoritative; never infer replies support from a token prefix alone or report missing email as missing history. Confirm applicable rate-limit category for the actual installation during certification. Slack currently documents different distribution-dependent limits; provider response and Retry-After control retries. [Slack history](https://docs.slack.dev/reference/methods/conversations.history/), [Slack replies](https://docs.slack.dev/reference/methods/conversations.replies/).
2. Each invocation claims bounded work via DB leases/fencing; no open DB transaction spans HTTP. Use configurable request/time/byte budgets, fair allocation between newest-history catchup, older-history pages and oldest-due thread revisits. Reserve work for every lane so busy recent traffic cannot starve reconciliation. Freeze each history scan's upper anchor; persist the cursor after its discovered roots are durably enqueued. On invalid cursor restart the anchored scan with dedup. A new newest-history scan overlaps its predecessor boundary and deduplicates exact message IDs.
3. Initial historical scan covers all provider-retained selected-channel history, not an arbitrary 30-day root limit. For each observed valid root, enqueue hydration even if reply_count is absent/zero when it is due for reconciliation. Seed known historical roots from existing canonical items. Revisit known roots round-robin with deterministic `(due_at,root_ts)` order; new replies to a root older than any recent history cap therefore arrive. Track cycle duration, oldest overdue work and provider retention floor. Unseen roots beyond Slack retention remain an explicit source gap.
4. Hydrate raw root plus replies to completion; do not reuse the existing root-stripping return value when refreshing an old root. Dedup repeated message IDs across pages, detect repeating cursors/inconsistent pagination, and preserve raw existence separately from eligible content. A page limit becomes resumable pending work, never a truncated successful thread. Before publication revalidate config/public status/fence; an expired worker cannot overwrite a newer worker. For non-snapshot Slack pages use overlap/reconciliation, and do not assert complete source deletion from a contradictory page sequence.
5. Publish atomically through the EXISTING `ingestItem` transaction in `lib/ingest/index.ts` (`runContextTransaction`, with `session.db` and item-path locks). Add a narrowly typed internal Slack publication option carrying verified scope, staged generation and job fence; it is not an API payload field or arbitrary callback. Invoke the single source-owned ledger writer with the SAME transaction session in both changed-body and unchanged-body branches before their successful return. Lock/check the job fence and config revision in that transaction, replace message metadata, increment durable data generation and acknowledge the thread job together with the item write. Any ledger/sink error rolls back item/version/context and job acknowledgement. No network call occurs in this transaction. Existing project upsert before the transaction can remain an idempotent empty project after failure; it is not contribution success. After-commit cache bust is best-effort because durable generation invalidates other workers; retries re-run the same staged generation safely. No outbox alternative or broad item-writer rewrite is needed.
6. Reconcile removals only from complete, trustworthy thread snapshots and existing definite-gone semantics. Keep deletion metadata for audited reconciliation but exclude removed messages from current evidence; no source text remains in staging/history/summary salvage. Preserve root tombstone/replier behavior, superseded-body forgetting, graph deletion retries and private-channel purge. Permission/429/timeout/empty or incomplete pages do not imply deletion. A failed/unverified channel read suppresses currently unsafe Slack evidence through existing access/read integration, retaining stored content for recovery; a confirmed-private channel follows existing purge. No new grants are made.
7. 429 schedules retry at Retry-After (no tight sleep), transient errors use capped exponential backoff with jitter, auth/scope refusal is actionable blocked configuration with explicit retry, sink failure leaves publication pending. Restart, manual Run now and scheduled ticks drain the same state. Manual retry must honor provider backoff. Persist structured counts/errors in `ingest_runs.meta` and channel state without tokens or raw content.

## Authorship, dates and corrections

Eligible personal work is a source-timestamped human-authored normal text message or thread broadcast (dedup the original ID). Preserve current bot text in the canonical transcript where already supported, but bot/system/service-account messages do not earn a person's work credit. Reactions and mentions do not earn credit. File-only messages and structural subtypes remain excluded with a reason; expanding attachment semantics is separate. Retain known guest/deactivated users as source identities and permit explicit/exact links to human roster members; do not auto-link bots. Tombstoned roots earn no current root evidence while live replies remain eligible.

Normalize source instants to UTC and retain the exact message timestamp. Timeline grouping remains UTC (current grouper behavior), and displayed Slack times/day labels must agree; member-profile/browser timezone does not change stored work dates. Window semantics remain the existing rolling 7/30-day duration with fixed request `now` and explicit upper bound; capture `now` once for SQL and grouping. UTC midnight and DST/browser timezone tests pin this. Edits change content eligibility/hash but never `occurred_at`; deleting a message removes its current count/day if no eligible message remains. Never manufacture intermediate days from first/last timestamps.

Resolve qualified authors using the shared identity resolver with strict error propagation. Slack auto-sync accepts only one exact verified provider email matching one roster/member-email-alias candidate; disable heuristic matching for Slack without changing unrelated provider behavior. Explicit stable link precedes email and manual conflict is preserved. Add explicit suppressed/unlinked state so auto-sync cannot immediately recreate an intentional unlink from the same email. Identity writer must enforce team membership, atomic conflict-safe uniqueness and audit outcomes; concurrent link/remap cannot silently win based on a stale read. OAuth/token save may succeed as a credential operation while identity fails, but response/status must say identity pending/conflict, not imply attribution succeeded.

For unlocked items, group active eligible ledger messages by mapped member/day; multiple accounts for one person collapse. Stable row ID uses canonical item ID, member ID and UTC day. `at` is latest actual message that day; include count, source message links and `source_item_id` for authorization. Root wording is allowed only on a day containing that member's actual root message; their later-day replies say “Replied in …”. Use source permalinks or a deterministic authenticated library link with source message details; no secret-based links.

For locked items, use the EXISTING credit oracle: only corrected owner, or nobody when cleared. Do not redistribute every historical participant day to the owner as if they authored it. If the corrected owner has actual mapped message evidence, show those days and suppress others; if not, show no invented authored day and expose the lock as the reason in authorized diagnostics. This preserves correction authority and factual day evidence without adding a new contributor override system. The credit oracle remains the shared owner of this decision.

Link/unlink/remap must enqueue scoped historical repair and invalidate all affected timeline/arc summaries immediately. Message ledger stores source identity, not a permanently trusted cached member ID, so reads resolve current mappings. Repair root-owner/version attribution through existing lock-respecting reattribution rules; do not rewrite source dates or blanket-clear all provider versions. Every repaired/skipped/locked/ambiguous count is reported. No message refetch is necessary to remap already verified ledger rows.

## Query, cache, API and UI

Read Slack ledger by `occurred_at` in SQL with AIOS team and current item visibility/provenance predicates BEFORE limits, joining existing items and canonical account mappings. Do not query by root work_at, synced_at, or a prelimited list of items. Aggregate `(item,member,UTC day)` before applying an evidence-page limit, so one busy thread never splits a day count. Order deterministically by day/evidence time, item ID and member ID. Supply keyset continuation for Slack evidence with bound window, view and generation; reject expired/incompatible cursors and require restart if attribution/source generation changes. The dashboard endpoint carries additive coverage/continuation for its UI, which loads more without duplicates or final-looking partial totals. Preserve the v1 timeline DTO `{window_days,days}`: internally drain Slack pages to a complete bounded-window result; if runtime/size budget prevents completion, return the existing actionable error response, never silently return a partial success. V1 need not expose pagination or freshness fields. Retain unrelated-source behavior.

Core identity/ledger/access read failure is an error, not an empty successful Slack leg. Preserve safe last-known data only if it can be reauthorized against current items/memberships and current attribution generation; remove/regenerate summaries whenever that is uncertain. Otherwise return actionable unavailable status. Successful empty is allowed only after a successful complete read. Distinguish `sourceCoverage` (pending/partial/blocked plus last read/full cycle), `ledgerFreshness` (computed time/data generation), `summaryStatus` and `continuation`. A summary outage leaves evidence visible, including unlinked-to-task evidence.

Use existing cache writer/purge helpers. Add a durable team Slack-data/identity generation checked on memory and persisted hits and before refresh publication; process-local bust alone cannot prevent another server publishing old attribution. Increment transactionally with source/mapping changes; compare-and-swap publication or retry discards an overtaken build. Item visibility revocation must already invalidate/purge variants through the access path; test unchanged project-set hash with changed item membership, and reauthorize stale fallback. Bump payload version from the then-current staging value and raise synopsis salvage floor for changed authorship/day meaning. Do not salvage a sentence across remap/deletion/data-generation change just because person/day matches.

Extend Admin integration/run diagnostics and existing People identity context/Admin identity editor with workspace name/ID, raw login ID, mapping status/provenance and authorized correction action. Keep credential health separate from identity health. Do not expose tokens, Slack email or internal failure details to unauthorized viewers. Reuse existing context visibility and admin/self edit boundaries; self-verified login cannot force another person's link. Slack diagnostics are admin-only and scoped to selected channel, optionally message ID/permalink; normal viewers receive only coverage of their visible evidence, never hidden-item counts.

## Migration, repair and rollback

Additive tables/indexes in `postgres/schema.sql`; any existing-table alterations also get timestamped migrations. Update architecture drift inventories; existing v1 API fields remain unchanged as above. Schema application must be repeatable from zero and from populated staging-era fixtures. Do not make HTTP calls or rewrite unknown historical attribution in schema migrations.

Ship a resumable admin repair command/service with explicit team/integration/channel scope, dry-run default and bounded batches. Reports inspectable legacy namespace matches/collisions, existing metadata, available source range, pending source reads, message/day counts, unresolved mappings and locked exceptions. Applying uses the same writers/queues as normal ingestion, keyed by repair ID and cursor. It refetches available threads to reconstruct actual dates; first/last participant metadata supplies only those individually attested endpoints if retained as explicitly partial legacy evidence, never synthetic intervals. Prefer showing existing legacy evidence marked partial until its item has a complete message ledger, then atomically replace it; never union old and new rows for the same item. Saturated legacy coverage must be labeled partial until migrated, not certified complete.

Feature readiness is per channel/item and records verified generation. Keep legacy identity rows, a durable item-path migration mapping, and additive tables through rollout. Rollback disables new readers/workers and invalidates cache/summaries; it must not delete ledger evidence or reverse mappings blindly. Old binary fallback cannot safely consume ambiguous namespaced data: hold affected Slack view unavailable/partial until a compatible build is restored. Record this limitation; no promise of transparent old-binary rollback. Production apply/canary requires separate authorization; local/staging fixtures and dry-run preparation do not.
